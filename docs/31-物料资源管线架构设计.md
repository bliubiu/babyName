## 一、概述

### 1.1 背景

起名引擎的质量上限由「物料资源」决定：八字排盘、五行喜用神、候选字池、诗词典故、谐音避讳、
笔画数理，全部依赖一套跨越多源、多格式、多体积的物料。调研发现这些物料当前分**两条轨道**运转，
虽已跑通（后端 `go build/vet/test` 全绿、两种运行模式 `e2e_check -strict` **18/18**），
但加载/持久化侧存在结构性重复与双真源风险，随物料持续扩充会持续放大维护成本。

**轨道 A — 离线批处理（源 → JSON）**：`backend/cmd/export_namer`、`export_data`、`export_wuxing`、
`build_frequency`、`build_namestats`（Go，产出主程序是 `export_namer`，`namer.json` 由它生成）
+ `backend/scripts/*.py`（爬取/清洗，`check_data*.py`/`verify_coverage.py` 等校验）。
采集/清洗外部语料（Chinese-Names-Corpus、chinese-poetry、chinese-xinhua、chineseStroke、
通用规范汉字表），归一化后产出 `backend/data/` 下 **35 个 JSON**（已核）+
`data/raw/kangxi-strokecount.csv`（**注意：CSV 在 `data/raw/` 下，不在 `data/` 根**）。

**轨道 B — 运行时装载（JSON → 内存 / SQLite）**：`data.Init` 统筹各域 loader 灌入内存索引，
再由 SQLite(WAL) 做镜像持久化。

### 1.2 设计目标

1. **单一装载协议**：以统一 `Material` 接口收敛**≥10 处**同构的 `Load*FromJSON/Reload*FromJSON`
   （实测清单见 §2.3.1）。
2. **声明式依赖**：用物料清单 `manifest` 声明 `dependsOn`，拓扑加载替代 `data.Init` 硬编码顺序。
3. **装载期强校验**：脏数据在装载期即确定性报错，取代运行时补丁（如 `normalizeGender` 事后补救）。
4. **单一校验真相源**：离线 `build_*`/`scripts` 与在线 loader 共用同一 Go schema 校验库。
5. **热更新闭环**：逐物料 diff 版本重载 + 原子 swap + 删除语义 + 观察者通知。
6. **最小侵入**：域消费与现有 **22** 包测试基线不破坏，分相落地。

### 2.3 结构性问题

1. **Loader 模式重复 ≥10 处**（原文「4 处」系漏计，ADR-001 的收敛范围以本条为准）：
   - 完整 `Load+Reload` 成对：`yijing/loader.go:13+33`、`zodiac/loader.go:13+33`、
     `hanzi/loader.go:46+137`、`classics/loader.go:13+65`、`hanzi/namer_loader.go:80+158`；
   - 单向：`classic_loader.go:195/214/233/265/286`（5 个 `loadXxxFromJSON`）、
     `fate/naming_quality.go:53`、`fate/semantic_filter.go:177`。
   - 共性均为「`ReadFile → Unmarshal → mu.Lock → 赋值`」，另各有各自的重载/回滚写法。
2. **顺序靠注释维持的隐式依赖**：`dataloader.go:20-66` 要求 kangxi 先于 namer、namer 先于
   覆盖/合并/频率；新增物料需人工插到正确位置，无依赖拓扑与失败回滚。该函数**同时存在 gofmt
   缩进不一致**（55-66 行多缩进一级），可作为「未经格式化护栏」的现存证据。
3. **运行时补丁**：`normalizeGender`（`namer_loader.go:152`，**非原文 :179**）因数据里 `男/male` 混用
   （实测：中文「男」155 字、英文 male 733、female 951、**空 6266**）在装载时才归一化——本质是
   「装载期缺校验」的既成事实补救。**且 `""` 未映射为 `neutral`**：空 gender 字在
   `adapters.go:595` 的性别筛选下会被整批剔除（归一语义变更，属行为变更，见 §五 P-1.4）。
4. **双真源字段缺口**：`queryViaSQL`（`adapters.go:538-603`）因 SQL 过滤维度不全，必须回查内存
   全量 `HanziData` 二次过滤（**回查代码在 `adapters.go:560-601`；声称「SQL 表无 gender/categories/
   radical」的注释实际在 `adapters.go:564`，非原文 :535**）。该注释与 `store.go:979-1017`
   实际写入这些列相悖——双源漂移的实证。
5. **大文件整读整解析**：`word.json`(26.1MB)、`shici.json`(6.6MB)、`bigram`(13.4MB) 全量
   `ReadFile+Unmarshal`。
6. **版本化 / 热更新不闭环**：多数 JSON 无 `version`；已带 `version` 的 `namer.json` 实测是**静态
   `"1.0"` + `generated:"2026-07-22"`**——**该值不随内容变更，无法驱动任何 diff**（ADR-014）。
   `ReloadAll`（`dataloader.go:69`）= 重新 `Init`、生产无调用方；合并语义实为
   **`INSERT OR IGNORE`（非 upsert）**，字段更新亦不生效（ADR-011）。
7. **拼音声韵无独立物料家**：音韵五音法（宫商角徵羽，见 `AGENTS.md 术语`）散落在 fate 层，
   未作为一等物料被加载/校验/版本化。
8. **`hanzi_data` 存在「空壳列」（本条为 ADR-011/012 的直接成因）**：
   `Hanzi` 结构（`hanzi.go:33-68`）**无 `Level` 字段**；`namer_loader.go:110-129` 注入 `HanziData`
   时也**未写入** `PhoneticScore/ModernScore/ClassicalScore/IsPolyphonic/GenderTags/PairBlacklist/
   CurationLevel`。而 `hanzi_data` 表（`store.go:246-270`）**有**这些列 → `seedHanziData`
   （`store.go:979-1017`）写入的是**默认值/空值**。即：表结构齐、内存无值、SQL 侧恒为空壳。

## 三、目标架构：统一物料资源管线（Materials Pipeline, MRP）

三层 + 一套协议，域消费层与 DDD 分层保持不变。

### 3.1 核心抽象（收敛 ≥10 处重复）

```go
// internal/materials/material.go
type Material interface {
    Name() string                       // "namer" / "classics.shici" / "phonology" / …
    Checksum() string                   // **内容指纹（sha256），diff 与门控的唯一依据**；Version 仅作可读标识
    DependsOn() []string                // 声明式依赖 → Registry 拓扑排序加载
    Fetch(src Source) (Raw, error)      // 读 JSON/CSV 或离线中间格式
    Normalize(Raw) (Normalized, error)  // 可组合 Steps：性别/五行/拼音/康熙/tier
    Validate(Normalized) error          // 装载期强校验：schema、取值范围、拼音/radical 合法性
    Apply(store *Store) error           // 写内存索引 + (可选) SQLite 镜像；原子 swap
}
```

- **Registry**：集中注册全部物料；`Bootstrap()` 按 `DependsOn` 拓扑排序 → 逐物料 `Validate` →
  `Apply` → 整体 checksum 写入 `data_meta`。任一物料失败在改动全局前即报错，不再落半截数据。
- **Store**：内存索引 + `checksum` + `sync.RWMutex`；`Reload(name)` = diff `Checksum` → 只重载变更
  物料 → 原子 swap → 通知观察者；补「本轮键集 ∪ 注入来源键集」差集删除（落定 `docs/30 §四` 待实施点）。

### 3.2 三层职责

| 层 | 包（拟定） | 职责 |
|---|---|---|
| L1 源/清单 | `materials/manifest` | 声明 `source · version · checksum · dependsOn`；与离线 `build_*` 同构 |
| L2 规范化/校验 | `materials/normalize` + `materials/validate` | 可组合归一化 Steps；装载期硬校验 |
| L3 装载 | `materials/store` | 内存索引仓储（版本戳/原子 swap）+ SQLite(WAL) 双写 + 拓扑加载 + 热更新 |

**最小侵入落地**：`Apply` 经薄 adapter 写现有域全局（`HanziData`/`NamerCharMap`/`FrequencyDB`/
`HexagramList`/各类 `*Extracted`——它们本就加锁且被广泛消费），**不动 fate/name/hanzi 引擎**；
新物料（`phonology`）走独立 store。既统一管线又不引发大重构。

## 六、架构决策记录（ADR）

> 每条 ADR 记录一个不可逆或影响面较大的决定；后果如实列出（含代价）。

### ADR-001：物料装载三层化（源清单 / 规范化校验 / 仓储）

- **状态**：接受（待实施）
- **背景**：**≥10 处** loader 同构复制、顺序硬编码、运行时补丁、双真源（§2.3.1）。
- **决策**：引入 `materials` 包，划为 L1 清单、L2 规范化/校验、L3 仓储三层，全部物料实现统一
  `Material` 接口，由 `Registry` 按 `DependsOn` 拓扑加载。
- **后果**：新增物料从「改多个 loader + 记住插入顺序」降为「实现一个 Material + 声明依赖」；
  装载顺序与失败语义可被确定性测试。代价：一次性搬迁期两种装载路径短暂并存（P0 用 adapter 兜底）。

### ADR-002：最小侵入——经 adapter 写现有域全局，而非替换数据结构

- **状态**：接受
- **背景**：`HanziData`/`NamerCharMap`/`FrequencyDB`/`HexagramList`/`*Extracted` 等全局已被
  fate/name/hanzi/handlers 广泛只读消费，且都已有锁保护。
- **决策**：`Material.Apply` 通过薄 adapter 写入这些既有全局，域引擎不动；仅新物料走新 store。
- **后果**：改动聚焦装载管线，blast radius 小，22 包测试基线与两种模式 e2e 全绿可维持。
  代价：内存「唯一真源」仍是域全局，而非集中 `Store`；后续若要彻底集中，可在 P2 之后以
  「Store 提供与现有 getter 同签名的访问器」平滑替换。

### ADR-003：SQLite(WAL) 双写 + 装载层统一投影

- **状态**：接受
- **背景**：`hanzi_data` 表列与 `Hanzi` 字段手工对齐且过滤维度不全，导致 `queryViaSQL` 必须回查内存
  二次过滤（§2.3.4）；`classics_*` 已有版本 diff 重建（`data_meta`）。
- **决策**：装载层统一负责「内存索引 ⇄ SQLite」双写；SQL 过滤所需列由装载层一次投影到位
  （补列 + **补齐投影值**，见 ADR-012），消除 Go 端回查。**写入语义统一为 upsert**（ADR-011）。
- **后果**：SQL/内存双读一致可被测试；字库下沉只需维护投影一处。代价：`hanzi_data` 需一次
  schema 迁移（`CREATE TABLE IF NOT EXISTS` + 新列 tolerant，或重建并重灌），且必须先完成
  P-1.1/P-1.2 否则「一致」无从谈起。

### ADR-004：装载期强校验，脏数据即拒

- **状态**：接受
- **背景**：`normalizeGender` 事后补救、非法日期/评分靠上游各写各的检查（`check_data*.py`/
  `verify_coverage.py`）。
- **决策**：`Material.Validate` 在装载期做 schema/范围/枚举/拼音/radical 合法性校验，失败即
  报错并中止该物料装载（不进全局）。
- **后果**：数据质量前移到装载期，可确定性回归（脏 fixture 即失败）。代价：需要为每种物料补
  校验规则与 fixture；对历史上「宽松加载」的物料是一次收紧。

### ADR-005：离线/在线同构 schema，单一校验真相源

- **状态**：接受
- **背景**：离线 `build_*`(Go) 与 `scripts/*.py`(Python) 各自校验/清洗，易漂移。
- **决策**：离线产物与在线装载共用同一 Go schema+校验库；Python 仅负责爬取/清洗到「中间标准
  格式」，最终规范化与校验统一由 Go 完成。
- **后果**：校验规则只维护一处。代价：`scripts/*.py` 需收敛为只产出中间格式，部分清洗逻辑
  迁移到 Go（分批迁移，优先 `convert_poetry`/`build_forbidden_combos`）。

### ADR-006：热更新 diff 闭环 + 删除语义

- **状态**：接受
- **背景**：`ReloadAll`=重新 `Init`、写入不删除也不更新、生产无调用方（`docs/30 §四`、§2.3.6）。
- **决策**：`Store` 记录每物料 **checksum**（非静态 version，见 ADR-014）；`Reload` 逐物料 diff
  checksum → 只重载变更 → 原子 swap → 通知观察者；合并区先构「本轮键集 ∪ 注入来源键集」再差集删除。
- **后果**：热更新最小化且有界；「热更新删字」终局正确。代价：引入观察者与版本比对复杂度；
  需 `name/reload_test.go` 式的死锁/超时守护测试。

### ADR-007：稳定物料「导入一次 · SQLite 为源 · 四档加载」

- **状态**：接受（待实施）
- **背景**：`word.json`(26MB) 被启动急载（`cmd/server/main.go:133`），是启动耗时与常驻内存最大头；
  `name_bigram_frequency.json`(13.4MB) 随 `LoadFrequencyDB` 在 `data.Init` 阻塞急载（Tier≥2 后约 7MB）；
  `shici.json`(6.7MB) 走异步；`full/given/gender_stats`(9.2/1.9/20MB) 是 `build_namestats` 离线产物、
  **运行时不加载**；各物料懒加载（sync.Once / ready 通道 / 有界等待）各写各的。
- **决策**：按「变更频率 × 访问特征」分 A 权威稳定 / B 周期重建 / C 追加 / D 纯离线 / E 用户数据；
  加载分四档——**T0 急载阻塞**（候选池底座 namer 8105 / 康熙 / 拼音声调 / 偏旁）、**T1 异步预热 +
  有界等待 + 降级**（shici / word / 频率库）、**T2 懒载**（偶发，`sync.Once`）、**T3 DB 按需查询**
  （海量点查，`words`/统计表，~不入内存）；稳定物料「离线 build → JSONL → `materials import` 单事务
  入库一次」，运行时按 `data_meta` 版本 diff 决定是否重导，**不每启动重灌**；行型大语料用 JSONL
  （流式解码 / 批量导入 / 行 hash diff / append），结构化小文档（namer/yijing/zodiac/kangxi）留单 JSON。
- **后果**：启动**阻塞段从 ≈38MB（word 26 + namer 4.7 + bigram ≈7 + 杂项）收敛到 ≈5MB**，word/bigram 移出
  关键路径；海量点查常驻内存≈0。代价：`word.json` 改异步/DB 需把取释义处改为可降级；新增 `words`/
  统计表与 `materials import`；JSONL 与 JSON 并存期双份产物。懒加载复用并泛化 shici 既有「Once + ready +
  recover + defer close + 有界等待」四件套，三条硬约束以 `shici_ready_test.go` 为范例补回归测试。
  **收益口径须按定档分列**（当前 §7-2 未定档，不得预先记「常驻内存大降」）：

  | 定档 | 启动阻塞段 | 常驻内存 |
  |---|---|---|
  | 现状（word 急载） | ≈38MB | 26MB+ |
  | T1（异步预热） | ≈5MB | **26MB 仍在**（仅移出关键路径） |
  | T3（`words` 表点查） | ≈5MB | ≈0 |

### ADR-008：SQLite 成为物料运行时唯一源（显式 import，运行时不再解析 JSON）

- **状态**：接受（设计，待实施；**受 P-1 四项前置约束**）
- **背景**：当前是 JSON→内存→`INSERT OR IGNORE` seed 库的**三源并存**；且 `adapters.go:564` 注释
  「SQL 表无 gender/categories/radical」与 `store.go:979-1017` 实际写入这些列相悖（双源漂移实证）。
- **决策**：运行时只认 SQLite 单一源——① **热数据启动从库载入 typed 结构**（namer/yijing/zodiac/
  **康熙**，后者落点见 ADR-013），**冷点查按需查库**（word 释义走 `words` 表），**全程不解析 JSON/CSV**；
  ② 归一化/校验从 loader 上移到 import，一次烘焙进库；③ `materials import` 写完整表并补齐缺口：
  `hanzi_data` 补列 `level/kangxiStrokes/nameFreqTier` **并补齐 8 个空壳列的投影值**（ADR-012），
  新增 `charGroups`(29 组偏旁分组小表)、`words(char PK, explanation)`、`kangxi_strokes(char PK, strokes)`
  三表，写 `data_meta` **checksum** 版本（ADR-014）；④ **触发方式 = 显式 `namer materials import` CLI +
  entrypoint「库缺失或 `data_meta` checksum 不匹配」才自动导入一次**；⑤ 移除启动 seeding 与运行时
  JSON 解析路径。
- **后果**：启动/常驻内存大降（word 26MB 出局）、单一真源消除漂移、归一化只跑一次、热更新=checksum bump，
  镜像可烘焙预建 `namer.db`；代价：多一个 import 构建步骤、**改 `data/*.json` 必须 re-import 才生效
  （行为变更，须写入 CLI 帮助与部署文档）**、库缺失需 fail-fast 引导，并以 round-trip 测试
  （import→读出 typed 结构 ≡ 现 JSON 路径）保行为等价。**前置代价**：P-1.1~P-1.4 必须先行，
  否则「SQLite 为唯一源」会把当前既存的字段投影缺失与写入失效一并固化进库。

### ADR-009：物料字段归一化——单一规范基座 + 导入期可组合 Steps + 即拒校验

- **状态**：接受（设计，待实施）
- **背景**：gender 男/male 混用（`namer_loader.go:152` 运行时补丁）、拼音多形态（`homophone.go:444`）、

- **决策**：每物料一个权威 `Canonical*` 基座（§9.2/9.3）；`materials/normalize` 用有序纯函数 Steps
  （Pinyin/Enum/WuxingDerive/Clamp/Merge）；`materials/validate` 分物料校验，失败带

### ADR-010：归一化产出 SQL 初始化数据 + 预构建 DB 作为上线交付物

- **状态**：接受（设计，待实施）
- **背景**：ADR-008 运行时只读 SQLite，需回答「库从哪来」；现部署是烘 87MB JSON + 启动 seed。
- **决策**：`materials import` 归一化后同时 `--emit-sql`（可 diff 可审计的可移植初始化脚本）与
  `--emit-db`（预构建二进制）；entrypoint **按 checksum 判定**决定是否灌 SQL；运行时只读开库。
- **后果**：上线零 JSON/零启动导入；`materials.sql` 是可审计初始化真相源、`namer.db` 是最快运行态；
  代价：构建多一个 emit 步骤（复用同事务）+ 必须满足确定性/幂等（§10.4：主键稳定排序、
  **upsert 语义与 `cp -n` 版本门控不得错配**、UTF-8 无 BOM、转义 helper、checksum 门控、
  **WAL 交付须含 `-wal`+`-shm`**），并有回归测试兜底。

### ADR-011：持久化写入语义 = 主键 upsert（修正「INSERT OR IGNORE 即幂等」的误解）

- **状态**：接受（P-1.1 立即实施）
- **背景**：`seedHanziData`（`store.go:979-1017`）实测使用 `INSERT OR IGNORE`——原文 ADR-010 把它当作
  满足「按主键幂等」的正解、原文 §2.3.6 把它描述为「upsert」。两者都不准确：**`INSERT OR IGNORE`
  使已存在的行永不更新，物料字段修订与删字都不会传导到 SQLite**，且每次启动仍全表扫描尝试插入。
  这意味着「SQL/内存双读一致」在当前实现下**已经不成立**。
- **决策**：装载层写 SQLite 一律 `INSERT ... ON CONFLICT(pk) DO UPDATE SET <受控列白名单>`；
  删除走「本轮键集差集 DELETE」。幂等定义为「同输入多次执行结果等价」，**而非「冲突即跳过」**。
- **后果**：物料修订与删字能正确传导，ADR-003 的双读一致性守护测试才有意义。代价：
  ① 每次启动需做一次差集删除判定（可用 `data_meta` checksum 短路：未变更则整段跳过）；
  ② 受控列白名单必须显式维护（新增列需同时加白名单，否则静默不更新——须有守护测试兜底）。

### ADR-012：单一 mapper 三目标投影（`Hanzi` / `NamerChar` / `hanzi_data`），补齐空壳列

- **状态**：接受（P-1.2 立即实施）
- **背景**：`Hanzi`（`hanzi.go:33-68`）无 `Level` 字段；`namer_loader.go:110-129` 注入 `HanziData`
  时未写入 `PhoneticScore/ModernScore/ClassicalScore/IsPolyphonic/GenderTags/PairBlacklist/
  CurationLevel`；而 `hanzi_data`（`store.go:246-270`）**有**这些列 →
  `seedHanziData` 写入的是默认值。**表列齐、内存无值、SQL 恒空**。
- **决策**：`CanonicalChar` 经**一个** mapper 同时产出 `Hanzi`、`NamerChar` 与 `hanzi_data` 行；
  `Hanzi` 补 `Level`；8 个空壳列必须有真实值来源（源数据无值时明确置 0/空数组并在 §9.8 记为
  「非空列可空值」，**不得以默认值伪装成有值**）。
- **后果**：消除「结构对齐但值不对齐」的隐性错位（`adapters.go:564` 注释漂移的根因之一）。
  代价：触及 `Hanzi` 结构（新增字段）与 `seedHanziData`，blast radius 中等（`Hanzi{...}` 字面量实测 11 处），
  须 22 包测试与 e2e 双向验证；部分列在补齐后会**首次出现非零值**，可能改变评分（须 golden 回归兜底）。

### ADR-013：康熙笔画落 `kangxi_strokes` 表（消除「运行时只读 SQLite」下的数据空洞）

- **状态**：接受（P-1.3 立即实施）
- **背景**：ADR-008 要求运行时「全程不解析 JSON/CSV」，但 §8.6 明确「kangxi 不落库」，且
  §8.5/§10 的建表清单**没有康熙表** → 运行时 `KangxiStrokes`（数理、卦象口径，AGENTS.md 要求
  「数理用康熙」）无来源。此为设计空洞，非实现细节。
- **决策**：新增 `kangxi_strokes(char TEXT PRIMARY KEY, strokes INTEGER)`，由 `materials import`
  从 `data/raw/kangxi-strokecount.csv` 导入一次；运行时从库载入为 typed map，`DependsOn` 声明
  `kangxi → namer`（`mergeKangxiStrokes` 依赖前置）。CSV 降级为 **import 输入，不再是运行时依赖**。
- **后果**：ADR-008 的「零 JSON/零 CSV 运行时」得以真正成立。代价：新增一张表与一段载入代码；
  需容忍「CSV 有、库无」的首次部署（库版本不含该表时按 0 处理并记 warn，不 fail-fast）。

### ADR-014：以 sha256 checksum 作为物料唯一 diff / 门控依据（`version` 降级为可读标识）

- **状态**：接受（P-1.4 立即实施）
- **背景**：实测 `namer.json` 的 `version` 是**静态 `"1.0"`**、`generated` 为 `"2026-07-22"`，
  内容变更时**不随之更新**。ADR-006/ADR-008 的「按版本 diff 决定是否重导」以此为依据将
  **永不触发**，热更新与「库过期自动导入」形同虚设；多数 JSON 更是连 `version` 都没有。
- **决策**：`Material.Checksum() string`（源内容 sha256）为唯一 diff 与门控依据；
  `data_meta` 增列 `checksum`，`version` 仅作可读标识展示；`materials.lock`（§11.4）登记源指纹，
  形成「上游 sha256 → 产物 sha256 → data_meta checksum」三级可审计链。
- **后果**：diff 可靠、门控可测（改 1 字节即 bump）。代价：每次装载需计算源文件 sha256
  （大文件 26MB 级约数十 ms，可用 size+mtime 做快速路径、命中后再算全量 hash）；

### 8.1 物料分类：变更频率 × 访问特征

| 类 | 物料 | 变更频率 | 访问特征 | 运行时现状（证据） |
|---|---|---|---|---|
| **A 权威稳定** | 通用规范汉字表 namer.json(8105)、康熙笔画、拼音声调、偏旁映射、词典 word.json、门禁表、经典文学语料 | 几乎不变（国家表/古籍，季度级） | 高频·点查 | namer 急载；**word.json 26MB 急载**(`main.go:133`)；shici 异步(`classic_loader.go:179`) |

### 8.2 四档加载策略（回答「何时加载」）

```
T0 急载阻塞(bind 前 Ensure, 常驻)   热路径必须有、体积小       → A: namer 8105 / 康熙 / 拼音声调 / 偏旁
T1 异步预热+有界等待+降级(Warm+Ensure) 大体积但会用到          → A: shici / word   B: 频率库
T2 懒载(sync.Once, 首次访问 Ensure)  偶发用到、非生成链路        → PDF 字体 fontOnce 等
T3 DB 按需查询(~不入内存)            海量·纯点查·非扫描          → words 释义 / 统计，走 SQLite 索引行查
```

- **T0 只留候选池底座**（namer/康熙/拼音/偏旁）：几 MB，`/names/generate` 每次必需，阻塞可接受。
  （注：ADR-008 落地后 T0 物料改为「从 SQLite 载入」，不再读 JSON/CSV；康熙落 `kangxi_strokes` 表，ADR-013。）
- **T1 是本次最大收益点**：`word.json`(26.1MB) 现被急载（`cmd/server/main.go:133`→`hanzi.go:96`），
  占启动急载 ~68%。释义是「非精选字兜底」点查（`WordMeaning(char)`，`hanzi.go:168`），应改
  **shici 同款异步预热**（甚至 T3 走 DB），把 26MB 移出启动关键路径。
- **T3 对海量点查最划算**：words/统计建 SQLite 索引表，`SELECT ... WHERE char=?`，常驻内存≈0、启动≈0。
- 合并后启动阻塞段 ≈38MB → ≈5MB（namer resident），bigram 归 T1。
  **T1 与 T3 的差异在常驻内存而非启动耗时**（对照表见 ADR-007 后果）。

### 8.3 懒加载技术：统一「四件套」

代码内已有被 `docs/24 P2-9` 硬化过的范式，应上升为 `Material` 层内建能力（`Warm()`/`Ensure()`），各域零散实现收敛：

```go
// 泛化 classic_loader.go:124-152 的既有实现
var once  sync.Once
var ready = make(chan struct{})
func Warm() { go func() { defer close(ready); defer recover(); load() }() } // ① recover+defer close 双保险
func Ensure() bool {                                                        // ② 有界等待+降级，禁无超时 <-ready
    select { case <-ready: return true; case <-time.After(30*time.Second): logger.Warn("降级：无 X"); return false }
}
```
- 现成同款：shici(`classic_loader.go:124`)、`frequency.go`(`freqDBOnce`)、`poetry_index.go:10`、
  `report_service.go:23`(`fontOnce`)。
- **T0/T1/T2 只是 `Ensure()` 时机差异**：T0 在 bind 前 `Ensure`（阻塞）；T1 启动 `Warm()` + 首次访问 `Ensure`（有界降级）；T2 仅首次访问 `Ensure`。
- **三条硬约束（血泪教训，docs/24 P2-9）**：`close(ready)` 必须 `defer`、加载协程 `recover`、等待必有超时——都要回归测试兜底（范例 `shici_ready_test.go` 7 例）。

### 8.4 JSONL 格式选型（行型大语料用 JSONL，结构化小文档留 JSON）

```
用 JSONL（一行一记录）                留单 JSON（整体结构化文档）
─────────────────────────────      ────────────────────────────
word.json 释义            26MB       namer.json(8105+charGroups 29 组) 小且整体有意义
name_* / bigram 统计      十几~二十MB  yijing(64卦) / zodiac(12) / forbidden_combos(962)
curated 自学习追加日志                  kangxi-strokecount.csv（结构化 CSV，行主键 char）
诗词/典籍语料（导入 SQLite）
```
- **收益**：① 流式解码、读大文件常数内存（不再整文件 `Unmarshal` 成大切片）；② 批量导入 SQLite 极简
  （批 N 行一 `INSERT`、可断点续跑、按行主键幂等 upsert）；③ 热更新 diff = 逐行 hash 比对；
  ④ 追加型（自学习/爬虫回流）天然 append-only，定期 compact 入库。
- **迁移（加法式，零破坏）**：build 同时产出 `*.json` + `*.jsonl`；loader「有 `.jsonl` 优先流式读，
  否则回落整读 `.json`」。先转 word.json 与统计两个大头；保持 namer/yijing/zodiac/kangxi 为 JSON/CSV。

## 九、物料字段归一化设计

> 把 L2「规范化/校验层」落到字段级：每种物料一个权威 `Canonical*` 结构；归一化在 `materials import`
> 完成一次并烘焙进库（ADR-008）；本节是 ADR-004/005/008/012 的字段级展开。基于已核实结构
> （`NamerChar` namer_loader.go:10、`Hanzi` hanzi.go:33（**无 Level 字段**）、
> `wordEntry` hanzi.go:89、`Char/BigramFrequency` frequency.go:12/13/21、
> `ShiCiEntry` classic_loader.go、`hanzi_data` store.go:246）。

### 9.1 原则

1. **单一规范基座**：运行时 typed 结构、SQLite 列、离线中间格式皆由 `Canonical*` 派生，消三源漂移。
2. **归一化只跑一次**：import 期完成，落库即规范态；运行时不 normalize。
3. **可组合纯函数 Steps**：`Record → Record`，有序、可单测、离线/在线同源（ADR-005）。
4. **显式优先级派生**：五行/康熙/频率/分类合并的冲突解决顺序写死且可测。
5. **脏数据即拒（ADR-004）**：校验失败报错并可归因到「物料+字段+值」。
6. **标度隔离**：score/tier/stroke/count 各有定义域，禁止互相占用。

### 9.2 规范字段基座 `CanonicalChar`（合并 NamerChar ∪ Hanzi，去冗余）


### 9.5 归一化管线（import 内有序 Steps，纯函数）

```
raw ─①Pinyin─▶ ②Enum(gender/tone/...) ─③StrokeDual ─④WuxingDerive ─▶
    ⑤CategoryInfer ─⑥MergeKangxi ─⑦MergeFreqTier ─▶ ⑧Clamp/Scale ─▶ ⑨Validate ─▶ Canonical
```
- **①Pinyin**：`stripTone`（homophone.go:444）同源——去声调符号、数字后缀(`wang2`→`wang`+tone=2)、`ɡ→g`、`ǖ→v`；产出 `PinyinASCII`+`Tone`。
- **②Enum**：按 §9.4 逐字段归一（含 gender 空值→neutral 的**行为变更标注**、多音字 tone 置 0）。
- **⑤CategoryInfer**：`NamingCategories` 空则 `ClassifyNaming(char,radical,meaning,wuxing)`（`hanzi/loader.go:80`）。
- **⑧Clamp/Scale**：score/penalty∈[0,100]、level∈{0..3}、usageLevel/curationLevel/tier∈[1,5]；默认越界 reject，白名单字段 clamp。

### 9.6 跨物料合并优先级（写死、可测）

`CanonicalChar` 派生 recipe：
1. 基座 = namer 记录（逐字权威字段）。
2. **康熙**：`KangxiStrokes = 库/CSV值 if present else 0`（只填该列，不动 `Strokes`；`namer_loader.go:231`）。
3. **五行**：`CharacterWuxingOverride(字义法) > 原JSON值 > GetWuxingByRadical(部首法) > ""`（hanzi.go:142）。
4. **频率档**：`NameFreqTier = FreqDB.tier if ≥1 else 0`（只填频率，不覆盖其它分）。
5. **分类**：`JSON标注 if 有 else classifier`。
6. 以上合并全部在 Validate 前完成，任一步失败即拒。

### 9.7 单位与标度（禁止互相占用，速查）

- 笔画：`Strokes`(简) / `KangxiStrokes`(康熙) 两套并列；数理用康熙，频率用简称。
- 评分：`0-100` 整型（positive/phonetic/modern/classical/curated.score）；DB `score` 用 REAL。
- 档位：`usageLevel/curationLevel/nameFreqTier` 均 `1-5`，`0`=未收录/未知。
- 等级：`level∈{0表外,1,2,3}`；`tone∈{0轻声,1-4}`。
- 计数：`frequency.count/rank`（非分数）；`meaning≤200 runes`。
- **铁律**：`score≠tier≠count≠strokes`；杜绝「字符承载数值」旧写法（quxiang 溢出、int 拒浮点）。

### 9.8 校验规则（分字段）

- **必填**：`Char`(单汉字)、`PinyinASCII`、`Strokes≥1`；`Poem.Paragraphs` 非空。
- **域**：`Wuxing∈{5}|""`、`Level∈{0..3}`、`Tone∈{0..4}`、各 score/level/tier 合界。
- **引用完整**：`Radical∈部首表`；`NamingCategories∈受控词表`(否则 reserved+告警)；`Dynasty∈枚举`。
- **跨物料**：`Bigram.key==Char1+Char2`；`Word.Char==[]rune(word)[0]`；`Hexagram.ID∈[1,64]` 唯一。
- **失败策略**：报错含 `物料/字段/值/规则` 并中止该物料；`--lenient` 仅取证不阻断（数据清洗期用）。

### 9.9 单一投影到存储（Canonical → `Hanzi` + `NamerChar` + `hanzi_data`）

**一个 mapper、三个目标、零漂移**（ADR-012，**已实施** `hanzi/mapper.go`）：
- typed：`Hanzi{...}`（已补 `Level`）/ `NamerChar{...}`（已补 `IsPolyphonic`）。
- SQLite `hanzi_data`：现有列 + **补 3 缺口** `level / kangxi_strokes / name_freq_tier`；
  **并逐项裁定 8 个历史空壳列的值来源**（实测 `namer.json` 的 char **仅 17 个字段**）：

  | 列 | 真值来源 | 处置 |
  |---|---|---|
  | `is_polyphonic` | `namer.json` `isPolyphonic`（**1279 字，15.8%**） | ✅ **补齐**（此前 `NamerChar` 未声明该字段而静默丢弃，是本次最大真实收益） |
  | `level` | `namer.json` `level`（3500/3000/1605） | ✅ 补列 + 补值 |
  | `kangxi_strokes` | CSV 合并（ADR-013） | ✅ 补列 + 补值 |
  | `name_freq_tier` | `name_frequency` 物料合并 | ✅ 补列 + 补值 |
  | `tone` | `namer.json` `tone`（仅 562） | ✅ 补齐现有值；回填见 §11.1 |
  | `phonetic_score` / `modern_score` / `classical_score` | **源无此字段** | ⚠️ 结构性空值，显式置 0，**不得用 `positive_score` 复制填充** |
  | `gender_tags` / `pair_blacklist` | **源无此字段** | ⚠️ 结构性空值，显式 `[]` |
  | `curation_level` | **源无此字段** | ⚠️ 结构性空值，显式 0 |

  即：8 个空壳列中 **4 个已补齐真值**（is_polyphonic / level / kangxi_strokes / name_freq_tier），
  **4 个确认为「源无真值」的结构性空值**（评分三项 + 两项标签 + curation_level），
  按「不臆造」原则显式留空并在此登记 —— **不得以默认值伪装成有值**（ADR-012 决策）。
- **写入语义**：单事务全量重建（ADR-011，偏差见文首 #1）。
- **订正 `adapters.go:564`**：列齐且值齐后 `queryViaSQL`（`adapters.go:538-603`）可去掉 Go 端回查
  二次过滤（`adapters.go:560-601`）—— **P2 进行中，见 §十一 11.9**。
- **守护测试**：`store_schema_guard_test.go` 断言「表列集合 == INSERT 列集合 == 占位符数 ==
  `hanziDataValues` 长度 == 补列清单无重复」，任一环节漏改即失败。

### 9.10 包结构与 TDD 验收

```
internal/materials/schema/    // Canonical* 结构 + 枚举 + 受控词表(部首/分类/朝代/生肖)
internal/materials/normalize/ // 可组合 Steps（Pinyin/Enum/WuxingDerive/Clamp/Merge）

internal/materials/checksum/  // 源内容 sha256 + data_meta 门控（ADR-014）
cmd/materials import          // raw → schema → normalize → validate → 单事务 upsert 入库 + data_meta
```
- **round-trip/golden**：raw 变体 → normalize → 等于 golden `CanonicalChar`。
- **脏数据**：`男/male`→male；`wánɡ/wang2/ɡ/ǖ`→`wang/tone`/`v`/`g`；score=150 reject；level=5 reject。
- **合并优先级**：override 胜部首；kangxi 只填 `KangxiStrokes`；`Word` 首字键。
- **多音字**：`IsPolyphonic==true` 时 `Tone` 不得由拼音猜出，置 0 并保留音位（守护测试断言 1279 例）。
- **投影一致**：`Canonical→hanzi_data→读回 ≡ typed`；`queryViaSQL` 回查移除后 SQL/内存双读字段级一致。
- **upsert 生效**：改 `namer.json` 单字段 → 重灌 → SQL 读回新值；删字 → SQL 同步消失。
- **checksum 门控**：改 1 字节源文件 → `data_meta` checksum 变更 → 触发重导。
- 复用 `namer_loader_test.go`/`frequency_test.go`/`shici_ready_test.go` 断言风格；错误信息全中文。

## 十、SQL 初始化数据与上线交付

> ADR-008「运行时只读 SQLite」的运维终局：归一化产物本就是「固定 schema 的行集」，可回落为**确定性
> 的 SQL 初始化数据**或**预构建 DB**，让上线「零 JSON、零启动导入」。

### 10.1 两种交付物（建议都产）

| 形态 | 命令 | 用途 | 特点 |
|---|---|---|---|
| **`materials.sql[.gz]`** | `--emit-sql dist/materials.sql.gz` | 可读、可 review/diff、可被任何 SQLite 工具执行 | 明文 INSERT，纯运维无需 Go；体积大可 gzip |
| **预构建 `namer.db`** | `--emit-db dist/namer.db` | **最快，"仅运行"**，运行时只读打开 | 零启动导入；镜像直接烘入 |

`materials.sql` = `CREATE TABLE IF NOT EXISTS …` + 分物料批量 **upsert**（按主键幂等，ADR-011）+ 一行
`data_meta` checksum；`namer.db` = 把同一次事务提交成文件，运行时 `?mode=ro` 直接用。
**注意**：`materials.sql` 面向「空库初始化」，幂等靠「主键 upsert」而非「冲突即跳过」；
把它灌进一个**已存在的旧库**时，若沿用 `INSERT OR IGNORE` 会得到「版本号是新的、数据是旧的」
静默不一致（见 §10.3 的处置）。

### 10.2 生成命令面

```
namer materials import --data ./data --emit-sql dist/materials.sql.gz --emit-db dist/namer.db
```

### 10.3 部署消费（Docker / 单机 / 开发者）

Docker（沿用现有 `*-seed` + `cp -n`，docs/30 §六）：
```sh
# docker-entrypoint.sh：库缺失或 checksum 不匹配才整库替换/灌一次
if [ ! -f "$DATA_DIR/namer.db" ]; then
    cp /seed/namer.db "$DATA_DIR/namer.db"                       # 预构建库：直接落盘
elif ! materials_checksum_ok "$DATA_DIR/namer.db" "$BUILD_CHECKSUM"; then
    # 旧库 + 新 SQL：必须「重建」而非「INSERT OR IGNORE 叠加」，
    # 否则 data_meta 版本变新而旧行不更新 → 静默不一致（ADR-010/ADR-011）
    rm -f "$DATA_DIR/namer.db" "$DATA_DIR/namer.db-wal" "$DATA_DIR/namer.db-shm"
    cp /seed/namer.db "$DATA_DIR/namer.db"
    # 仅当预构建库不可用时的兜底（可选，需 sqlite3 CLI）：
    # gzip -dc /seed/materials.sql.gz | sqlite3 "$DATA_DIR/namer.db"
fi
exec ./namer-server
```
- **`cp -n` 的 no-clobber 与 checksum 门控互斥**：`cp -n` 会保留旧库，后续用 SQL 灌库又不会更新
  旧行 → 版本与数据错配。故此处改为「不存在则 cp；checksum 不符则**重建替换**」，不再依赖 no-clobber 叠加。
- 单机/桌面：`namer.db` 挨着可执行文件；缺失则提示/自助 `namer materials import`。`sqlite3` 只作**可选
  fallback**，主路径是烘入的 `namer.db`，运行时零外部命令。

### 10.4 确定性要求（否则 SQL 初始化不可信）

1. **字节稳定/可 diff**：行序按主键排序；`data_meta` 只放 `物料+version+checksum`，**不含 `built_at`**
   （时间戳放旁路文件）。**唯一性前提**：凡依赖「源文件顺序」的归一化（如词典首字选取，§7-5）
   必须先固定规则，否则排序即改变结果。
2. **幂等**：一律 **upsert by PK**（ADR-011）；`materials.sql` 仅用于空库或整库重建；
   重建式替换（§10.3）而非 no-clobber 叠加。
3. **UTF-8 无 BOM + 转义**：`'`→`''`、换行进参数；用**被测过的转义 helper**，中文/生僻字（含 CJK 扩展）按 UTF-8 直写。
4. **checksum 门控**：`data_meta` 为 `key/value/updated_at` 的 KV 表（`store.go:197-201`，**不新增列**），
   按约定 key 存 `materials.<物料>.checksum` 与 `.version`；运行时/entrypoint 比对 checksum 决定是否重导
   （§8.5 fail-fast）。**`version` 不作门控依据**（ADR-014）。
5. **journal 模式**：预构建库以目标 journal 模式落盘；只读打开不再执行 `PRAGMA journal_mode`
   （docs/28 W7）。**WAL 交付必须成组三件套** `namer.db` + `namer.db-wal` + `namer.db-shm`：
   `?mode=ro` 打开 WAL 库仍需要 `-shm`（缺失则无法建立共享内存索引）；**只读文件系统下直接失败**。
   故推荐 `--emit-db` 时以 `journal_mode=DELETE`（或 `VACUUM INTO` 产出自包含单文件）落盘。
6. **体积**：`materials.sql.gz`（8105+bigram+poetry 约十几 MB → gzip 数 MB）；`namer.db` 同理。

### 10.5 三种上线场景

| 场景 | 交付 | 运行时 |
|---|---|---|
| Docker/K8s（compose+nginx） | 烘 `namer.db`（+`materials.sql.gz` 可选兜底）为 seed | entrypoint 按 checksum **重建替换**（非 `cp -n` 叠加），backend 只读开库 |
| 单二进制桌面 | `namer.db` 挨着 exe（建议自包含单文件 journal） | 直接只读；缺失则引导 import |
| 开发者 | `materials.sql`（可 diff/golden） | 按需灌**空库**或直连 |

### 10.6 闭合链路与收益/代价

```
build/爬取 → JSON/JSONL/CSV ─归一化(§9)→ Canonical ─▶ materials.sql / namer.db ─▶ 部署上线
运行时：只读 SQLite（ADR-008），不碰 JSON/CSV；改物料 = 重新 import 出新 SQL/DB，checksum bump 触发重导
```
- **收益**：上线从「烘 87MB JSON + 启动解析/seed」降为「烘一个库 + 只读」；`materials.sql` 提供**可审计、
  可 diff 的初始化真相源**，`namer.db` 提供**最快的运行态**。
- **代价**：构建期多一个 emit 步骤（复用 `materials import` 同一事务，增量代码很小）；须保证 §10.4 的
  确定性与幂等（有对应回归测试）；**并须先完成 P-1 四项前置**（§五），否则会把现存字段投影缺失
  与写入失效一并烘焙进「权威库」。

② **组合级过滤**：`IsBadCombo`(forbidden 实测 962)/`IsHistoricalFigureCombo`/`IsNonNamingCombo`/`PairBlacklist`；
③ **音韵连读**：`CheckAllBadHomophones`/`CheckBadPinyinCombo`(含姓氏连读)；
④ **风险分级体检**：`AssessNameRisks`（pass/warn/fail：表外字 fail、三级字 warn、多音字 warn、硬禁用 fail、
   软惩罚祈福豁免、敏感字 warn、撞名分档）。
路线图保留该 defense-in-depth 分层；门禁物料分 `CanonicalGate`(字级) 与 `CanonicalForbidden`(组合级) 两类分别归一（§9.3）。
> **主题边界提示**：§十二「门禁层落地实践」与 §一~§十一（物料管线）是**两个独立议题**，
> 建议拆出为 `docs/32-门禁层设计与运营闭环.md`（并与本设计 §九 的 gate 物料归一交叉引用）。

### 11.1 数据质量层（最大杠杆，含实测）
- **声调回填（修订）**：import 期由 `PinyinRaw` 派生 `Tone`，可覆盖**单音字**（实测 tone 仅 **562**/8105
  = 6.93%；原文「563」有误）。**但实测 1279/8105（15.8%）为多音字，单值 `Tone` 在结构上无法表达** →
  多音字**不得为覆盖率编造声调**：置 `Tone=0`、保留音位列表、平仄评分对多音字降权或走 phonology 消歧。
  可回填的准确上限约 **6826 字（84.2%）**，非「~100%」。**高收益/中成本**。
- **寓意评分补全**：由释义关键词+分类规则/模型生成 `positive_score`（实测仅 **563**/8105 = 6.95%）。中成本。
- **字段完整度记分卡+门禁**：CI 断言各字段覆盖≥阈值（实测 meaning **89.2%**/radical **97.09%**/
  level 3500/3000/1605/namingCategories 100%/isPolyphonic 1279/isRare 99/isNegative 14）。低成本。

### 11.2 可观测 / 可运维层（当前基本缺）
- go.mod 无 metrics 库；`/readyz` 仅查一字（main.go:359）。
- **启动物料报告**：每物料 版本/条数/耗时/是否降级，结构化落日志。
- **`/readyz` 增强**：加「已装载物料版本 == 构建版本」探针，缺料/过期即 not-ready。
- **checksum 校验**：装载前验 `data_meta` checksum，损坏 fail-fast（不静默降级）；
  **并作为版本 diff 的唯一依据**（ADR-014，§7-2 的 `version="1.0"` 不可用）。

### 11.3 领域建模层：全局态 → 仓储注入（架构红利最大，成本最高）
- 现状：`HanziData`/`NamerCharMap`/`FrequencyDB` 等仍为包级全局可变 map（虽有锁），域/handler 直读——
  难隔离测试、热更新全局耦合。
- 方向：引入 `CharacterRepository`(及 `PoetryRepository`…) 接口 + 防腐层(ACL)，由依赖注入装配到
  fate/name/services；全局 map 降为默认实现，逐步替换直读。
- 中间态（低成本先行）：**schema 漂移守护测试**——断言 `CanonicalChar` ↔ `hanzi_data` 列 ↔ typed struct
  三向一致（`adapters.go:564` 注释漂移的护栏）。**此项已上提为 P-1.2 的交付物**，不再列为「后续项」。

### 11.4 多源归一 / 供应链治理
- **姓氏多源归一**：`baijiaxing.json`/`surname_stats.json`/build_frequency 内 `compoundSurnames+surnameSet`
  并存 → 统一 `surnames` 物料，一处生成。中收益/低成本。
- **`materials.lock` 供应链清单**：记录每物料 上游源(repo+commit/URL+sha256)+生成命令+产物 sha256；
  `scripts/*.py` 依赖容器化固定。高收益(可复现/审计)/中成本。

### 11.5 测试与 CI 门禁层
- **物料刷新流水线**：CI 跑 `materials import → validate → 完整度阈值 → e2e_check -strict → golden names diff`。
- **golden names 快照**：固定生辰 Top10 排名快照，防评分静默漂移（docs/30 §九 记录过一次性异常）。
- **归一化属性测试**：幂等性 `norm(norm(x))==norm(x)`、数值 clamp。

### 11.6 字符集层
- **CJK 扩展区**：RareChars 硬编码含扩展字，扩展 B 多缺拼音/笔画→被 `IsRare`/笔画≤25 过滤；建议改从数据源取笔画/拼音。低-中收益/中成本。
- **繁→简映射物料**：`sanzijing-traditional.json` 已存在，建 繁→简 映射供语料去重/对齐。中收益/低成本。

### 11.7 仓库与编码卫生（quick win，均已实测）
- `.gitattributes` 补 `*.go text eol=lf`（现文件已有 `sh/conf/yml/json/csv/md`，**确缺 `*.go`**）；
  文档声明遵守「UTF-8 无 BOM」，但 `data/raw/` 存在 **GBK 乱码文件名**
  （如 `Ancient_Names_Corpus��25W��.txt`、`wuxing_��.txt`），跨平台/CI 风险 → 源文件重命名为 UTF-8。
- **`gofmt` 未纳入 CI**：`gofmt -l` 当前列出数十个文件（如 `adapters.go`、`dataloader.go` 缩进不一致），
  建议 CI 加 `gofmt -l` 零告警门禁。
- **工作区洁净度**：未提交项 **127**（原文「94」已过时），需按 CalVer 打包提交。
- `backend/tools/` 混放 `.go`/`.py`/`.exe`（`e2e_check.exe` 8.8MB 未入库但存在于工作区），
  非标准 `cmd/` 布局，建议 `.gitignore` 补 `*.exe` 并按 Go 惯例重组目录。

### 11.10 P2 实施记录（2026-10-14，commit 见 §11.9）

**目标**：ADR-003「SQL 与内存结果等价」——消除 `services` 层逐字 `hanzi.GetHanzi` 回查。

**原病灶**（实测确认）：
- `SearchHanziByFilter` 只返回 6 列，`services` 拿不到 `gender / naming_categories /
  radical / level / kangxi_strokes / meaning / is_rare`；
- 故 `queryViaSQL` 与 `FindCharacters` **两处**各做一次逐字回查（后一次还是纯重复劳动——
  `queryViaSQL` 已过滤完，`FindCharacters` 又把结果丢回内存重建）。SQL 下沉收益归零。

**实施**：
1. `database.Hanzi` 补 7 字段（`Level/KangxiStrokes/Gender/Radical/NamingCategories/Meaning/IsRare`）；
2. `SearchHanziByFilter` 的 SELECT 补齐对应列，`naming_categories` 的 JSON 数组
   在驱动层解析，**解析失败按「无分类」处理而非丢整行**（否则单条脏数据会连带丢掉该字全部属性）；
3. 新增 `databaseHanziToCharacter`（SQL 行 → `fate.Character`）；
4. 抽出 **`deriveCharacterFlags(level, strokes, isRare)`** 作为两条路径**唯一共有的派生规则**
   ——这是等价性的关键：差别只在输入来源，判定规则必须同源；
5. 两处回查全部删除。

**实施中暴露的 2 个真实数据缺陷**（守护测试 `filter_integration_test.go` 当场抓出，非本次引入）：

| # | 缺陷 | 影响 | 处置 |
|---|---|---|---|
| A | `hanzi.Hanzi.IsRare`（namer.json，99 字）与 `hanzi.RareChars`（编译期静态表，含 CJK 扩展区）**有 102 字不一致** | 只取其一时，同一字在两路径下 `IsRegular` 得到**相反**结论 | 两条路径统一取**并集**（任一侧判生僻即生僻，取保守侧）。守护测试 `TestRareCharUnionAcrossPaths` |
| B | 五行修正 `ApplyWuxingOverrides`（字义法覆盖表 > 已有值 > 部首字形法兜底）**只在内存侧生效**，import 直接落 `namer.json` 原值 | 实测 **14 字** `hanzi_data.wuxing` 为空而内存有值 → 五行过滤结果不一致 | 抽出无状态 `hanzi.ResolveWuxing(char, current, radical)` 作单一真源，内存与 import **共用**；`ApplyWuxingOverrides` 降为批量应用 |

**刻意保留的 1 处内存依赖**：`hanzi.IsCuratedNamingChar` 与 `hanzi.RareChars` 是
**编译期静态常量表**（非物料数据、不随 import 变化、无 I/O），查表不构成「回查」。
`curated_names` 属运行时自学习数据，尚未纳入统一 import（§11.9 第 4 项）。

**守护测试**：`adapters_p2_test.go` 以「返回内存中不存在的字」反证回查已消除
（若仍有回查，这些字会被 `if !ok { continue }` 丢弃，测试必失败）；
`filter_integration_test.go` 的 SQL/内存集合等价断言在修复后转绿。
