## 1. kangxi_strokes 按 hanzi_data 字符集裁剪评估

### 1.1 现状（实测）

| 指标 | 数值 |
|---|---|
| `kangxi_strokes` 总行数 | 63,696 |
| 不在 `hanzi_data` 的孤儿 char | 55,858（**87.7%**） |
| 在 `hanzi_data` 中且有康熙笔画的 char | 7,838 |
| `hanzi_data` 中**缺失**康熙笔画的 char | 267（占字库 3.3%） |

运行期 `LoadKangxiStrokesFromDB`（`store_kangxi.go:83`）把整张表载入内存字典 `hanzi.SetKangxiStrokes`，且只收 `strokes>0` 的条目。候选池只在 `hanzi_data` 字符集内选字，因此那 55,858 个孤儿 char 在运行期**永远不会被查询**——纯属冗余存储与导入开销。

### 1.2 裁剪收益与方案

- **收益**：行数 63,696 → 7,838（**-87.7%**），导入写出与内存字典同步缩小；对运行期行为**零影响**（查询集合是 `hanzi_data` 子集）。
- **方案（二选一，均不破坏 importNamer 的 deps 注入）**：
  - A（推荐，最简单）：在 `importKangxi` 落库后、`runImport` 提交前，追加 `DELETE FROM kangxi_strokes WHERE char NOT IN (SELECT char FROM hanzi_data)`。前提是 `importNamer` 已先于 `importKangxi` 写入 `hanzi_data`（需核验 `Import()` 的物料拓扑顺序，见 §1.3）。
  - B：在 `importKangxi` 解析阶段，从 `namer.json` 源读出 char 集合做预过滤（不依赖落库时序）。
- **连带问题**：裁剪不解决「267 个字库字缺康熙笔画」。这 267 字在运行期按 `kangxi_strokes` 缺失回落简体笔画，属口径不一致，应单独补全（`kangxi-strokecount.csv` 漏收或 namer 字符集超出 CSV 覆盖）。

### 1.3 时序风险（必须确认）

`Import()` 在分发前通过 `resolveImportDeps` 预解析康熙源注入 `importNamer`（`hanzi_data.kangxi_strokes` 列由此外部填充，不回读库）。若 `importKangxi` 在 `importNamer` **之前**执行，方案 A 的 `NOT IN (SELECT ... hanzi_data)` 会拿到空/旧集而误删。需先核对 `materials` 注册表里的导入顺序（working memory 记为 `importNamer` 为 `hanzi_data` 唯一写入方，但二者相对顺序未明），再定方案。

> **结论**：kangxi 裁剪**建议做**，高收益低风险；但需先确认物料拓扑顺序。它解决的是"表体积/内存冗余"，**不改变** `hanzi_data` 自身的列结构——所以与 Q2 的"列裁剪"是两件独立的事，后者另评。

## 2. hanzi_data 字段精简评估

`hanzi_data` 共 26 列、8,105 行。逐列空值/常量核查结果：

### 2.1 恒为空（全 8,105 行空）的列

| 列 | 类型 | 代码是否读写 | 判定 |
|---|---|---|---|
| `gender_tags` | TEXT `[]` | 写入（import/load/INSERT）、`mapper.go` 透传、运行期无解引用 | **死列（源无真值）** |
| `pair_blacklist` | TEXT `[]` | `adapters.go:354` 透传；`engine.go:1147` 有 `if len(ch.PairBlacklist)==0` 消费分支 | **恒空但被读取**（永远走"无禁忌"分支） |

证据：`mapper_test.go:82-86` 明确断言 *"genderTags / pairBlacklist 应为空（物料无此值）"*，证实**源 `namer.json` 从不提供这两个字段**（JSON `omitempty` 省略）。`adapters.go:423` 注释：*"pair_blacklist 上游无真值（内存侧实测 0 字有值）"*。

### 2.2 恒为 0 / 常量（全行同值）的列

| 列 | 类型 | 运行期是否参与评分 | 判定 |
|---|---|---|---|
| `phonetic_score` | INTEGER | 否（仅 normalize/mapper 透传，fate 引擎与 rater 从不读） | **恒 0 预留列** |
| `modern_score` | INTEGER | 否（同上） | **恒 0 预留列** |
| `classical_score` | INTEGER | 否（同上） | **恒 0 预留列** |
| `curation_level` | INTEGER | 否（同上） | **恒 0 预留列** |
| `updated_at` | TIMESTAMP | 否（导入时间戳，全部同一值 `2026-10-14 14:33:5x`） | **伪常量** |
| `positive_score` | INTEGER | **是**（`engine.go`/`rater.go`/`poolsize` 真实消费，出典/扣帽逻辑） | **活列，保留** |
| `naming_categories` | TEXT | **是**（`adapters.go:435` 消费，优先 SQL 值，空时 fallback） | **活列，保留** |

证据：`mapper_test.go:70-80` 断言 *"phoneticScore / modernScore / classicalScore / curationLevel 应为 0（物料无此值）"*；fate 评分层 grep 结果中，`PositiveScore` 大量出现而 `.PhoneticScore/.ModernScore/.ClassicalScore/.CurationLevel` **仅在 normalize/mapper 透传链路出现，从未进入 `rater.go`/`engine.go` 评分计算**。

### 2.3 部分缺值（非恒空、值得补全）的列

| 列 | 空行数 | 占比 | 说明 |
|---|---|---|---|
| `radical` | 236 | 2.9% | 缺部首，影响按部首筛选 |
| `meaning` | 875 | 10.8% | 缺释义，影响释义画像/出典展示 |
| `style_tags` | 7,542 | 93% | 仅 563 字有风格标签 |

### 2.4 评估结论与建议

- **"是否需补全"**：`gender_tags`/`pair_blacklist`/`*_score`/`curation_level` 是** schema 演进式预留字段**（代码已为其留好读写通道，只是物料管线当前无数据源）。补全 = 改造 `namer.json`/物料管线以产出真实值，属**二期物料扩充**工作，非库表问题。
- **"是否需清理"**：**不建议现阶段从 `hanzi_data` 删列**。原因：
  1. 收益有限：每行约少 5 个字段，8,105 行约省 150–200 KB（库占比 <1%），且 SQLite 对 `DEFAULT` 短值存储极省。
  2. 回归风险高：删列需同步改 `store.go` INSERT（25 列）、`loadHanziFromDB` 的 SELECT+Scan（18 处）、`mapper.go`、以及 `store_materials_import_classics_test.go:290-299` 等一连串断言。
  3. `pair_blacklist` 在 `engine.go:1147` 有解引用，删列会编译失败，需改引擎逻辑。
- **建议动作**：
  - 短期：维持现状（演进式 schema），在 schema 注释/文档标注这 6 列为"预留未填"。
  - 中期：若要计算音韵/古今/文白评分，先在物料管线产出 `phonetic_score/modern_score/classical_score`，再让其进入 `rater.go`——届时这些列自会"由死变活"。
  - 缺值补全：`meaning`(10.8%)、`radical`(2.9%) 建议从 `raw/hanzi.json` 等源回填，直接提升释义画像覆盖率。

> **结论**：hanzi_data 不存在"错误/冗余到必须清理"的列，6 列恒空/恒 0 是**有意的预留位**；优化方向是「二期补全数据」而非「删除列」。这与 Q1 的 kangxi 裁剪是两回事。

`excludedClassicsFiles`（`:189`）排除 `hanzi.json / word.json / curated_names.json / standard_chars.json / zodiac.json`（这些不是经典语料）。

### 3.2 入库映射（4 张表）

导入逻辑 `importClassics`（`store_materials_import_classics.go:28`）：

1. **`classics_books` + `classics_sections`（骨架）**：逐文件 `importClassicsFile` 解析。`baijiaxing`/`qianziwen` 走特殊解析，其余走 `importGeneric`（先试数组、再试对象）。单个文件解析失败**记日志跳过**（写入 `res.Reason`，可见非静默）。
2. **`classics_extracts`（起名字集，核心运行期数据）**：`classics.ExportExtractSets()` 物化——对每首诗词逐字提取、去停用词、按 char 从 `hanzi_data` 补全拼音/释义/五行/性别（不反规范化冗余列，docs/34 E-A）。`PRIMARY KEY(material, char)`，`seq` 保留码点升序（候选池注入顺序依赖）。
3. **`classics_poem_entries`（诗词索引）**：`classics.ExportPoemEntries()` 物化整首诗词，`content`/`tags` 按原序落库（顺序即语义）。

### 3.3 运行期使用链路

`LoadClassicsFromDB`（`:142`）装载（前置：字库已装载，否则字集属性无法补全而 fail-fast）：

```
classics_extracts ──► LoadExtractSets ──► 内存字集（17 个 material）
                                        │
                                        ├─► FindPoetryByChars(char)      → poetryFound（出典加分，engine.go:631/636）
                                        ├─► GetPoetryCharList("论语")    → 按源取字集（rater.go:402，source 加分）
                                        └─► GetBigramScore(char1,char2)  → 语义搭配分（rater.go:537/1371）

classics_poem_entries ──► LoadPoemEntries ──► 出典描述（FindPoetryByChars 返回的 desc，API 展示"出自《诗经》"等）
classics_books / sections ──► 骨架，运行期基本无读取（仅导入时建）
```

`poetryFound` 经 `engine.go` 传入 `charPotentialScore`（`:1116`）：有出典的字在潜力评分中获加成；`GetBigramScore` 提供「意蕴搭配」维度（如"逐/求"出自同一典故）。

### 3.4 ⚠ 关键发现：元曲/乐府/辞赋/易经「进了索引、没进字集」

实测 `classics_extracts` 的 17 个 material（合计 33,539 字）**不含** `yuanqu / yuefu / cifu / yijing`，但 `classics_poem_entries` 里这四类的诗词条目**全部存在**：

| source（poem_entries） | 首数 | 是否在 extracts 字集 |
|---|---|---|
| 元曲 | 10,934 | ❌ 缺失 |
| 唐诗三百首 / 宋词三百首 / 水墨唐诗 / 唐诗补录 | 926 | ✅（shici 覆盖） |
| 诗经 | 305 | ✅ |
| 乐府诗集 | 197 | ❌ 缺失 |
| 楚辞 | 65 | ✅ |
| 辞赋 | 47 | ❌ 缺失 |
| 易经 | — | ❌ 缺失（且 poem_entries 也无独立易经诗词，易经走 `yijing_hexagrams` 卦象表） |

根因：`classic_loader.go` 的 `LoadFromJSON` 字集提取 dispatch **只有 5 个 load 函数**——
`loadShiJingFromJSON`、`loadChuCiFromJSON`、`loadGuWenFromJSON`、`loadShiCiFromJSON` + 通用 `loadClassicFromJSON`（覆盖标准 `{content:[{chapter,paragraphs}]}` 格式的四书/蒙学）。**没有 `loadYuanQu / loadYueFu / loadCiFu / loadYiJing`**，因此这四类从未被 `extractFromEntries` 提取为起名字集。

而 `classics_poem_entries` 由 `ExportPoemEntries` 生成、覆盖所有 `classicsFileCategory` 源，故索引里齐全。

**影响**：用元曲/乐府/辞赋里的字起名时，`FindPoetryByChars` 查字集恒返回 false → `poetryFound=false`，**这些经典的字无法获得出典加分**，且其「按源取字集」(`GetPoetryCharList("元曲")`) 无数据。但**出典描述展示**仍可用（poem_entries 有）。易经不进字集可能属有意（卦象走 `yijing_hexagrams`），但元曲/乐府/辞赋属**明显遗漏**。

### 3.5 建议

1. **补齐字集 dispatch**：为 `yuanqu/yuefu/cifu`（以及确认是否需要 `yijing`）新增 `loadXxxFromJSON`，或在 `LoadFromJSON` 中以标准 `{content/paragraphs}` 适配器统一接入 `extractFromEntries`。注意 `yuefu.json`/`cifu.json` 顶层是 `{content: "字符串"}`（非 paragraphs 数组），需先拆句；`yuanqu.json` 是 `{paragraphs:[...]}` 数组，可直接复用 `loadClassicFromJSON` 思路。
2. 补完后重跑 `materials import`，`classics_extracts` 应新增 3–4 个 material，字集总量上升，元曲/乐府/辞赋出身的字起名时将正确加分。
3. 建议在 `materials import` 输出或 `materials status` 中**显式报告每类经典的「字集提取数 / 诗词条目数」**，使当前这种"索引齐全但字集缺失"的静默遗漏可在巡检中发现。
