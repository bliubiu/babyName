## 3. 算法层面（Pipeline Performance）

### A1. ⭐⭐⭐ N² 笛卡尔积的"早停"重设计

**问题诊断**：
- 当前 worker 早停只看 `local.IsFull() && combined < minScore * 0.6`（engine.go:614-623）
- `local` 是 worker 私有表，**不知道其他 worker 的高分**——容易做"无用功"
- 早停阈值 0.6 是**写死魔数**，没有自适应
- 25 万次组合中 ~80% 在过滤层被剔除，**但 5 万次实际进入评分的组合**中，~30% 可被全局早停拦截

**位置**：`engine.go:614-631`

**方案**：
1. **全局 Top-K 分数共享**（每个 worker 读 `global * 0.7` 而非 `local * 0.6`）：
   ```go
   var globalMinScore atomic.Int64
   // worker 周期同步：每 1000 次评分更新一次
   if local.IsFull() {
       minScore := local.MinScore()
       for {
           old := globalMinScore.Load()
           if minScore >= old { break }
           if globalMinScore.CompareAndSwap(old, minScore) { break }
       }
   }
   ```
2. **自适应阈值**：随剩余候选数动态调整
   - 前期 0.5 宽松（保留长尾）
   - 后期 0.7 严格（聚焦高分）
3. **跳过已饱和五行组合**：5×5=25 种组合每种 1 个代表，TopN 之后只需**单组合排序**

**预期收益**：N=500 时评分计算量从 ~25 万 → ~5-10 万（**5× 加速**）

**风险**：全局 atomic 写入竞争；阈值过严可能漏掉好名（需回归测试覆盖）

### A2. ⭐⭐ RatingWorkerPool 化

**问题诊断**：
- 当前 7 个 Rater 在 `RateName` 中**顺序**调用（rater.go:57-98）
- 每个 Rater 内部还有 I/O 密集操作（classics.GetBigramScore 仍走锁、YinYunRater 字符串处理）
- 单组合评分实际耗时 ~50-200 μs，**串行浪费 CPU**

**位置**：`rater.go:57-98`

**方案**：
1. **Rater 接口加 `IsAsync() bool`**：标记可异步化（如 BigramRater、WenHuaRater 的 I/O 部分）
2. **per-call goroutine pool**（bounded 池避免无限创建）：7 个 Rater 拆成 DAG，依赖链结束后合并
3. **预计算批处理**：把 N 个候选的 "bigram 查表" 打包成单个 goroutine，批量 Redis-style 处理

**预期收益**：双名评分耗时 -40~60%（CPU 充裕时，2-4 核下收益最大）

**风险**：goroutine 调度开销在小批量时反而亏损；需根据 N 动态选择串行/并发

### A3. ⭐⭐ 评分维度的"提前剪枝"

**问题诊断**：
- 当前评分对**所有候选**都跑 7 个 rater
- 实际很多候选在前 2-3 个 rater 就可判定"必不入榜"（如 wuxing 严重不符的组合，wuxing 维度 < 50）
- 当前 7 rater 全跑一遍 = ~50 μs/候选 × 5 万 = 2.5s

**位置**：`rater.go:57-98`

**方案**：
1. **早期终止（rater-level）**：rater 内部基于当前累计分预测"最终 < 全局 Top-N 末位"时，直接返回 `Score: -1` 信号
2. **流水线顺序重排**：把"区分度最大"的 rater 排前
   - WuxingRater（权重 0.24）+ 命理大维度 → 早判 24 分差距
   - YinYunRater（权重 0.14）→ 声调区分
   - WenHuaRater 共现 → 仅在前面高分时再评
3. **基于 i×j 评分的预测**：worker 维护"前 K 个候选的分数直方图"，新候选进 Rater 前先看潜力分是否可能进位

**预期收益**：评分调用 -20~30%，质量不变

**风险**：rater 顺序重排可能改变最终分数（需对比固定顺序与优化顺序的 TopN 重合度 ≥ 90%）

### A4. ⭐⭐ ExcellentTable 的自适应容量策略

**问题诊断**：
- `excellentTableCapacity = 10000` 是 hard-coded（table.go:12）
- `ensureWuxingDiversity` 取 `topCount * 10` 进 diversity pool，5×冗余
- worker 端**当前**已用 `topCount*2`（P2 方案5 修复），但主表仍 10000
- 每个 ExcellentEntry ~200 字节 × 10000 = **2MB 浪费/请求**（8 worker × 2MB = 16MB 峰值）

**位置**：`table.go:12, 78`

**方案**：
1. 把主表容量也从 10000 改成 `topCount * 4 + diversity_overhead`
2. 增加 `PoolSizeHint()` 公开容量策略
3. **rebalance on overflow**：堆满时按"分数分位数"淘汰而非简单"最低分淘汰"——保证 25 种五行组合各占一席
4. 内存优化：每个 ExcellentEntry 改为 `*ExcellentEntry` 指针池，按需分配

**预期收益**：单请求内存 -50%，微秒级 latency 降低

### A5. ⭐⭐ Poisson-Disk Sampling 做多样性采样

**问题诊断**：
- 当前 `ensureWuxingDiversity`（engine.go:1017-1056）是**贪心算法**——按分数+五行分组
- 局部最优，可能让某些"中分但五行稀有"的名字落选
- 实际效果：TopN 中可能"金金/木木"密集，"水土/火金"缺

**位置**：`engine.go:1017-1056`

**方案**：
- 用 **Poisson-Disk Sampling**（按"分数距离" + "特征距离" 双维度采样）
- 候选保留判据：分数 ≥ K-th 最高分 + 与已选集合的最小距离 ≥ radius
- 替代"每五行组合一个"硬规则，让分数与多样性平衡

**预期收益**：TopN 的"视觉差异"更好，间接提升用户体验

**风险**：需要调参 radius；过严会"金金/金土"重复，过宽则五行多样性失效

### A6. ⭐ Start 状态机化

**问题诊断**：
- `session.Start(ctx)` 立刻启动 goroutine，调用方仍可调用 `Wait()`
- 但 `Start` 后立即调 `ExcludeChar` 等可能在 goroutine 启动前发生，存在 race
- 注释（engine.go:281）说"短暂加锁，复制快照后立即释放"——这本身就是性能瓶颈

**位置**：`engine.go:97-117, 280-288`

**方案**：
1. 引入 `started` atomic.Bool 状态机：Pending → Starting → Running → Finished
2. 启动前的所有 Exclude* 写入"待应用"队列；Start 时一次性合并
3. 减少锁持有时间

**预期收益**：避免竞态 + 启动 latency -10%

### J1. ⭐⭐ 流式 Top-K 算法（算法 + 数据结构联合）

**问题诊断**：
- 当前 ExcellentTable 用 **min-heap**（container/heap）
- 25 万次 TryPush，每次最坏 O(log 10000) ≈ 13 次比较
- 全程都 push，不论是否入榜

**位置**：`table.go`

**方案**：
1. 改用 **Count-Min Sketch** 或 **Lossy Counting** 算法：
   - 第一轮：每个候选先入 sketch（O(1) 摊销），分数压缩为 4-bit
   - 第二轮：仅对高频候选（频率 > threshold）做精确评分
2. 或 **HyperLogLog-style 采样** + **Quantile Sketch** 找出 TopK

**预期收益**：双名评分 -40%（大量低分候选跳过精确评分）

**风险**：近似算法会改变 TopN 排序；需回归测试保证 Top10 准确率 ≥ 95%

---

### J2. ⭐⭐ WuxingRater 的表驱动化

**问题诊断**：
- WuxingRater 7 个判断分支（rater.go:147-247）
- 实际只需要"生/克/泄"三态枚举，可压缩为表驱动

**位置**：`rater.go:147-247`

**方案**：
- 预计算 `wuXingRelation[wuxing1][wuxing2] → "生" | "克" | "泄" | "泄入" | "中性"` 的查找表
- `Rate` 退化为 2-3 次 map 查 + 评分表驱动
- 编译期生成的常量数组替代运行时 map

**预期收益**：WuxingRater 速度 +50%

**风险**：低（纯重构，逻辑等价）

### J3. ⭐ RateName 的 SIMD 友好化

**问题诊断**：
- `RateName` 中大量 if-else + 字符串比较，CPU 流水线浪费
- Go 编译器无法自动向量化

**位置**：`rater.go:57-98`

**方案**：
- 把**整型评分**（命中数、笔画差）转为 `math/bits` 位运算

- 对 hot loop 加 `-gcflags=-d=ssa/cse/debug=1` 编译优化验证

**预期收益**：微秒级优化，对延迟敏感场景有意义

**风险**：可读性下降，维护成本上升

**问题诊断**：

## 4. 数据层面（Data + Memory + Persistence）

### D1. ⭐⭐⭐ Hanzi 数据的冷热分层

**问题诊断**：
- `hanzi.HanziData` 是 8105 字全表 map，每次 `FindCharacters` 都全量遍历
- 实际上 80% 查询关心的是"五行+笔画范围"——只有几百字命中
- 冷数据（稀僻字、3 级表外字）占内存却很少被评分用到
- 当前全表 ~4.5MB，65% 是冷数据

**位置**：`hanzi/hanzi.go:66`、`adapters.go:139-181`

**方案**：
- 内存分两层：
  - **热层**：level 1-2 常用字 (~6500 字) — Go map（同步）
  - **冷层**：level 3 + 异体字 (~1600 字) — `sync.Map` 懒加载（首次访问时建索引）
- FindCharacters 流程：先查热层 → 未命中再查冷层 → 全未命中查 SQLite
- 内存节省：热层只占 ~3MB（vs 当前全表 ~4.5MB），冷层按需加载

**预期收益**：内存 -30%，冷数据 0 启动开销

**风险**：冷层懒加载可能让首次访问慢 ~5ms

---

### D2. ⭐⭐⭐ 候选池增量构建（per-FilterOption LRU）

**问题诊断**：
- 当前 `FindCharacters` 每次请求都重新过滤
- 同一 FilterOption（性别+笔画范围+五行）下，候选池**变化极小**（仅 ExtraChars 注入变化）
- 双名笛卡尔积 N² 是 hot path——N=500 时就是 25 万次

**位置**：`adapters.go:139-181`、`fate/engine.go:255-260`

**方案**：
- **per-FilterOption 候选池缓存**（LRU，容量 100）：
  ```go
  type filterKey struct {
      Gender      string
      MinStrokes  int
      MaxStrokes  int
      Wuxing      string
      Regular     bool
      Nameable    bool
  }
  type candidateCache struct {
      mu      sync.RWMutex
      entries map[filterKey][]*fate.Character
  }
  ```
- Key = `FilterOption` 指纹
- Value = `[]*fate.Character`（过滤后候选）
- 命中时**直接复用**，节省过滤开销（~5-20ms / 次）
- **TTL**：候选池 5 分钟过期（避免 ExtraChars 长期不更新）
- **缓存预热**：热门组合（不限五行+不限笔画）启动时预计算

**预期收益**：重复请求 latency -60%（缓存命中），CPU -40%

**风险**：缓存 key 不一致会导致脏数据；需对 FilterOption 哈希一致性做严格测试

### D3. ⭐⭐⭐ BigramDict 的 LRU 预计算

**问题诊断**：
- `bigramIdx` 启动时构建一次，但 session 内不再更新
- 25 万次 `GetOrCompute` 中，未命中 cache 的部分仍要走全局 RLock
- 当前 SessionBigramCache（commit `27b8d64` 已落地）只缓 session 内结果——**首次冷查询仍开销大**

**位置**：`classics/bigram.go`

**方案**：
- 启动时预热：把 `hanzi.HanziData` 中**所有 (a, b) 对**（去重后 ~30万）一次性写入 SessionBigramCache
- 预热后双名评分阶段**100% 命中** cache
- 内存：30万 × 16 bytes = **4.8MB** / session（可接受）

```go
// engine.go Start 后批量预热
s.bigramCache.Warmup(func(a, b string) BigramResult {
    return BigramResult{
        Score:      classics.GetBigramScoreFast(a, b),
        SourceDesc: classics.GetBigramSource(a, b),
        Found:      true,
    }
})
```

**预期收益**：BigramScore 部分 latency 趋近 0，节省 12 万次 RLock 全部消失

**风险**：启动时间 +200ms（可接受）

### D4. ⭐⭐ Bigram 索引的 BloomFilter 预筛

**问题诊断**：
- 即使有 cache，**冷门字符对**首次查询仍要穿透到 `bigramIdx` 全 map
- 单次 RLock 仍 ~100ns，对 hot path 不可忽略
- 实际上 ~70% 字符对根本不在 bigramIdx 中（namer 8105 字 × 理论 3300 万对，只有 ~30万命中）

**位置**：`classics/bigram.go` GetBigramScore 入口

**方案**：
- 在 `SessionBigramCache` 前置 `bloom.Filter`（大小 1M bits，~120KB）
- 未命中 bloom 立即返回 `Found=false`，**跳过 RLock + map 查询**
- 误判率 < 1%，对 GetBigramScore 这种"是否命中"语义完全够用

**预期收益**：BigramScore 路径 -30%（cache miss 阶段）

**风险**：bloom 序列化/反序列化成本（可常驻内存解决）

---

### D5. ⭐⭐ ExtraChars 注入的预索引化

**问题诊断**：
- 诗词/经典来源的 ExtraChars 注入是动态路径
- 每个 ExtraChar 都要查 `hanziToCharacter`（O(1) map 查）+ 检查是否已存在（O(N) 遍历）
- 大量 ExtraChars 注入时（诗经全量 ~500 字）耗时可观

**位置**：`fate_name_service.go:211-248`

**方案**：
- 启动时为每个 Source（诗经/楚辞/论语/...）建立**预索引**：`map[char]struct{}` 用于 O(1) 去重
- 合并时直接 `_, exists := idx[char]`，避免 O(N) 线性查
- 缓存：每个 Source 的 ExtraChars 一次性算出，session 内复用

**预期收益**：ExtraChars 注入 -50%（200+ 字源时）

---

### D6. ⭐⭐ RatingCache（跨 session 持久化）

**问题诊断**：
- 同一 (a, b) 在**同 session 内**不会重复评分（ExcellentTable.seen 去重）
- 但**跨 session**完全重算——比如用户改个字辈后重新提交

**位置**：`application/services/fate_name_service.go:54-90`

**方案**：
- 全局 LRU cache `(surname, char1, char2, filter_fingerprint) → score`（容量 10000，TTL 1小时）
- 命中率：~30%（用户微调常见）
- 序列化：评分结果（不是 fate.Character）+ 缓存到 SQLite 或内存 LRU

**预期收益**：重复请求 -30%

**风险**：缓存 key 哈希碰撞会返回错误结果；需用强力哈希（SHA-256）保证

---

### D7. ⭐ PostgreSQL 适配层

**问题诊断**：
- SQLite 单机写锁瓶颈——多用户并发写入 history/favorites 时锁竞争
- 无跨服务器数据共享
- 无内置全文索引（汉字 LIKE 查询走全表）

**位置**：`infrastructure/database/sqlite/store.go`

**方案**：
- 加 `PostgreSQLStore` 实现 `database.Store` 接口
- 使用 GIN 索引（pg_trgm）支持汉字/拼音模糊查询
- 现有 SQLiteStore 保留作为单机/嵌入式模式
- 通过 `StoreType=postgres|sqlite|memory` 配置切换

**预期收益**：并发写 +10×；模糊查询 +100×

**风险**：需要 PostgreSQL 实例；运维成本上升

---

### P3. ⭐ Bigram 启动并行化

**问题诊断**：
- Bigram 共现统计在 `buildBigramIndex` 阶段是 N²
- 63700 字符 × 6 诗集 × 100+ 句子，循环量 10^8 级
- 单线程构建 ~500ms

**位置**：`classics/bigram.go:41-126`

**方案**：
- 启动时一次性用 `sync.WaitGroup` 并发处理各诗集
- 每个诗集用位图（`[]uint64`）记录字符出现，位运算快速求交集
- `errgroup` 限制并发数 = CPU 数

**预期收益**：启动时间 -30%

## 5. 架构层面（生产化）

### P1. ⭐⭐ OpenTelemetry 可观测性

**问题诊断**：
- 端到端 latency 无 Prometheus 指标
- Rating 阶段无 tracing span
- 排障靠 print + 日志，定位慢查询要逐函数 add log

**位置**：全栈

**方案**：
- 引入 OpenTelemetry：
  - span: `fate.generate` → `fate.findCharacters` → `fate.candidateIter` → `rate.wuxing` → `rate.wenhua`...
  - metric: `fate_name_duration_seconds{result}`, `fate_pool_size`, `fate_cache_hit_rate`
  - trace sampling: 1%（生产）/ 100%（调试）
- Grafana dashboard：TopN 5、9、99 latency + 评分缓存命中率

**预期收益**：问题定位时间 -80%

---

### P2. ⭐⭐ A/B Testing 框架

**问题诊断**：
- 评分权重改了 → 无法量化效果
- 不同用户对名字偏好差异大（地区/时代/性别）

**位置**：`fate_name_service.go:54`

**方案**：
- 在 FateNameService 入口加 `experiment` 字段
- 不同实验组用不同 Rating 权重（如 A 组：BigramRater 0.09 → 0.12）
- 反馈数据离线关联分析

**预期收益**：决策可数据化

**风险**：实验组用户分流要确保统计显著

---

## 6. 不建议做的（避坑）

- ❌ **GPU 加速评分**：评分逻辑是分支密集型，GPU 加速比 < 1×
- ❌ **机器学习替换 Rater**：数据量不够（用户反馈 < 10K），容易过拟合
- ❌ **Redis 缓存会话状态**：增加运维成本，单机内存已经够
- ❌ **微服务拆分起名引擎**：CPU bound 任务微服务化增加网络开销，纯亏
- ❌ **过度抽象接口**：当前 `Rater` 接口已经够用，过度抽象会拖慢开发
- ❌ **极致 SIMD/AVX 内联汇编**：Go 不支持，维护成本远超收益
