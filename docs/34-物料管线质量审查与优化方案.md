# 物料管线实现质量审查与优化方案

> 审查对象：`backend/internal/materials/**` + `backend/internal/infrastructure/database/sqlite/store_materials_*` + `backend/cmd/materials`
> 审查日期：2026-10-16
> 参照设计：`docs/31-物料资源管线架构设计.md`、`docs/32-物料管线落地改造实施计划.md`、`docs/33-门禁层设计与运营闭环.md`
> 方法：静态走读 + `go build`/`go vet`/`go test` + 覆盖率核查

---

## 一、整体评估

物料管线已具备**清晰的分层、强可测性与较好的工程纪律**：规范基座单一来源、拓扑排序 + 依赖闭包、事务内全量重建、可归因校验、`sha256` 内容指纹门控、注册表 fail-fast、订阅链路 append-only + 可回滚。整体达到"良好实现"水平。

但存在一类反复出现的**一致性/口径债务**（与本项目历史缺陷模式"双口径"高度吻合），以及若干"文档/注释宣称但未落地"或"防御性薄弱"的点。下面按严重度列出，并给出分阶段优化方案。

---

## 二、质量亮点（已做对的地方）

1. **规范基座单一来源**：`schema.Canonical*` + `Registry` 是离线 JSON / 中间格式 / SQLite 三态的唯一真源，新增物料只登记一行（`docs/31` ADR-001）。
2. **导入顺序可靠**：`schema.TopoSort` 带环检测；`resolveMaterials` 广度优先补齐依赖闭包，导入 `--only namer` 会自动带上 `kangxi`。
3. **事务骨架幂等**：`runImport` 在单事务内 `DELETE + INSERT` 全量重建，失败回滚；部分物料失败不影响已提交物料，下次仅重灌失败项。
4. **校验可归因**：`validate.Error` 携带 `material/field/value/rule`，`Errors.sorted()` 保证回归可比对。
5. **归一化不臆造**：`ValidWuxing("")` 合法、`normalize.Gender("")` → `neutral`（实测 6266 字无性别标注，不归一会整批误剔除）。
6. **指纹门控正确依据**：`checksum.File` 用内容 `sha256` 而非静态 `version`（namer.json 的 version 恒为 "1.0"），热更新/过期重导才真正触发。
7. **注册表 fail-fast**：`init()` 中未登记且非 legacy 的物料直接 `panic`，把"漏改 switch/定义/DDL 三处"的静默跳过变成启动期崩溃。
8. **订阅链路可审计**：`subscribe` 补丁 append-only、`Invert` 得反向补丁、`release.jsonl` 记录每次动作，灰度发布可回退。
9. **测试覆盖**：`schema/normalize/validate/checksum/review` 五包 **100%** 语句覆盖。

## 三、问题清单（按严重度）

### P0 — 一致性与正确性（潜伏债务，当前 e2e 绿但随时可能暴露）

**P0-1：`hanzi_data` 双口径写入**
- `importNamer`（`store_materials_import.go` → `wordValues`，约 L499）从 `namer.json` 经 merge 后写入 `hanzi_data`；
- `rebuildHanziData` / `seedHanziData` / `ReloadHanziData`（`store.go` L1085 `hanziDataValues`、L1127、L1184）从**内存态 `hanzi.HanziData`** 投影写入，**共享同一 `hanziDataInsertSQL` 但字段派生口径不同**。
- 现状：`seedHanziData` 经全仓检索**无生产调用方**（仅测试引用），`hanzi_data` 生产环境只由 `importNamer` 写。但这两条路径并存 + 字段来源不同 = 一旦 `seedHanziData`/`ReloadHanziData` 被误用（如纯 JSON 启动或热更新回调），即产生"双口径"污染。`docs/32` 也将此列为下轮剩余项。

**P0-2：跨物料合并依赖"依赖物料已落库"**
- `importNamer` 在合并康熙笔画、人名频率档时，直接从只读连接 `s.db` 回读 `kangxi_strokes` / `name_frequency`（`store_materials_import.go` L371–L406）。
- `Store` 的 `readDB` 是 `?mode=ro` 只读池（`store.go` L81，`SetMaxOpenConns(16)`），与 `writeDB` 是**不同连接池**。合并正确性隐含依赖两件事：① 上游物料已在本次/上次运行中落库；② WAL 下只读连接能看到 `writeDB` 的已提交数据。
- 首跑隐患：拓扑序中 `frequency DependsOn namer`，即 `frequency` 排在 `namer` **之后**。单次全量首跑时 `namer` 执行合并，`name_frequency` 尚未导入 → `namer` 读到**空 tier**，靠随后 `importCharFreq` 的 `UPDATE`（L646–L662）补救。结果正确但纯属**顺序巧合**，且代码注释本身也承认这一脆弱性。

**P0-3：`name_freq_tier` 两处维护、隐式顺序依赖**
- `importNamer` 读库设置 `NameFreqTier`，`importCharFreq` 又用 `UPDATE` 覆盖。两者口径须永远一致，且依赖 `importCharFreq` 在 `importNamer` 之后执行。属典型"双口径/双维护"坏味。

### P1 — 健壮性与可靠性

**P1-1：`checksum.Cache` 未接入导入链路（宣称未落地）**
- `checksum.Cache`（`checksum.go` L57–L92，size+mtime 快速路径）全仓**仅在测试中出现**；`importOne` 实际每次调用 `checksum.File` 全量重算（`store_materials_import.go` L168）。
- 注释称"避免每次启动对数十 MB 物料重算 sha256"，但该优化并未接线。要么接线，要么删除类型与注释，避免误导。

**P1-2：`materialUnchanged` 对"允许空表"的物料误判**
- `materialUnchanged`（`store_materials_import.go` L194）要求物料**所有** `Tables` 均非空，否则永远判为 changed。若某物料的辅表（如 `char_groups`）合理为空，该物料每次都会重灌，违背指纹门控初衷。

**P1-3：装载报告漏报 optional 物料**
- `LoadMaterialsFromDB` 会载入并返回 `allowlist`、`compliance_redline`（`store_materials_load.go` L48–L53），但 `materialNames()`（L478–L483）**未含这两项** → `LoadMaterialsFromDBWithReport` / `VerifyMaterialsFromDB` 永远不把它们计入 loaded/missing，启动 fail-fast 漏报这两类物料缺失。

### P2 — 可维护性与工程整洁

**P2-1：`store_materials_import.go` 单文件 1054 行，样板重复**
- 各 `importXxx` 高度同构（读文件 → `json.Unmarshal` → `normalize.*` → `validate.*` → `runImport`），每个 30–60 行样板。注册表已抽象一层，但每个 importer 仍手写大量重复。

**P2-2：校验错误上限截断（maxImportErrors=20）**
- 大批量脏数据只报前 20 条，且缺少"按规则聚合计数"，定位成本高。

**P2-3：`release.Promote` 非原子替换**
- 直接 `writeFile(activePath, cand)` 覆盖生效文件（`release.go` L207）。极端中断可能留半截 active 文件（虽有 history 存档可恢复，但 active 文件瞬时损坏窗口存在）。应"写临时文件 → fsync → rename 覆盖"。

**P2-4：sha256 实现两处重复**
- `subscribe.HashBytes/HashFile` 与 `materials/checksum` 包功能重叠，建议统一到 `checksum` 包。
- 标识符小问题：`schema.Word.ClassicalSc` 缩写命名（应为 `ClassicalScore`）。

## 四、优化方案（分阶段）

### 阶段 A — 收敛一致性（高优先，根绝"双口径"再现）— ✅ 已实施（2026.10.16.12）

- **A1 收敛 `hanzi_data` 写入口径** ✅：legacy `seedHanziData`/`rebuildHanziData`/
  `ReloadHanziData`（内存 `hanzi.HanziData` → `hanziDataValues` 投影）经全仓核查
  **无生产调用方**（仅测试引用），且字段派生口径与 `importNamer`（`namer.json` →
  `wordValues`）不一致，已整体移除。`importNamer` 成为 `hanzi_data` 唯一写入方。
  配套删除 `store_checksum_gate_test.go` / `store_hanzi_seed_test.go`，共享助手
  `newTestStore` 移至 `store_testhelpers_test.go`；`store_schema_guard_test.go` 的
  行值守护由 `hanziDataValues` 改锚 `wordValues`。
- **A2 解耦跨物料合并** ✅：`Import()` 分发前经 `resolveImportDeps` 从源文件预解析
  康熙笔画，通过 `ImportOptions.deps`（`importDeps`）注入；`importNamer` 不再回读
  `s.db`。彻底去掉"依赖物料已落库 + WAL 跨连接可见"两个隐含前提，部分导入
  （`--only namer`）同样成立（`TestImport_只导入指定物料并自动补齐依赖` 已加断言）。
- **A3 `name_freq_tier` 单一来源** ✅：新增 `Store.syncNameFreqTier`，在 `Import() 末尾
  以 `name_frequency` 表为唯一真源、用一条 `COALESCE` 子查询 `UPDATE` 完成清零 + 回填
  （仅 Tier ≥ 2）。`importCharFreq` 内的 `UPDATE hanzi_data` 已移除。归一化与
  「本次是否有物料真正落库」解耦——全部物料被指纹短路时依然执行，
  `TestImport_全部短路时仍归一化档位` 守护该语义（旧实现会失败）。

**用户追加决策**：`namer.json` 已包含全部三级候选字，`word.json` 不再需要加载/读取/使用。
据此在阶段 A 内一并移除 `word` 物料全链路（schema 定义 / `importWords` / `words` 表 DDL /
`loadWordsFromDB` / `materialNames` 条目）与 `hanzi` 域层 word.json 运行时加载
（`LoadWordData`/`WordMeaning`/`SetWordMeanings`/`WordEntry`，均无生产调用方），
以及 `cmd/namer-cli` 的 `LoadWordData` 调用。

**验证结论**：
- `go build ./...` / `go vet ./...` ✅；`go test ./...` 全绿（25 个有测试包）；
  `schema/normalize/validate/checksum/review` 五包 **100%** 覆盖。
- 真实数据全量导入：kangxi 63696 / namer 8105 / name_frequency 2237 / name_bigram 124994
  等 10 项写入、0 失败；`hanzi_data.name_freq_tier` 与 `name_frequency`（Tier ≥ 2）
  **逐字不一致数 = 0**（1118 字）；康熙合并覆盖 7838/8105 字；`words` 表不再创建。
- 二次导入：12 项全部按指纹短路，`tier>=2` 仍为 1118、字库仍 8105（幂等）。
- `e2e_check -strict` **双模式均 18/18**：模式二（DB 优先，新灌库）、模式一（空库回落 JSON）。
- 兼容性：改动前生成的旧库（含 orphaned `words` 表）直接启动正常，`/names/generate` 返回 200。

### 阶段 B — 清理与接线 — ✅ 已实施（2026.10.16.13）

- **B1 处置 `checksum.Cache`** ✅（选择删除）：`Cache`/`Stat`/`StatOf`/`Forget`
  全仓从未接线，且 size+mtime 快速路径在「等长修改 + mtime 未变」（git checkout /
  CI 复刻）场景下会漏判物料修订——用正确性换不存在的性能（单次导入每个源文件
  只 hash 一次，缓存无收益；word.json 26MB 退场后最大物料为 kangxi CSV 6.4 万行，
  全量 hash 约数十毫秒）。类型、测试与包注释一并移除。
- **B2 修正 `materialNames()`** ✅：改为从 `schema.Definitions` 派生
  （新增 `IntegratedMaterialNames()`，剔除 legacy 物料），「导入侧接入集合」与
  「装载侧报告集合」收敛为单一真源；`allowlist`/`compliance_redline` 不再漏报。
  守护测试 `TestMaterialNames_覆盖全部已接入物料` 写死期望列表，新增接入物料
  必须同步补装载分支，否则测试失败。
- **B3 `materialUnchanged` 放宽** ✅：只校验主表（`Tables[0]`，`schema.Definition`
  增加约定注释），辅表合理为空（如 namer 的 `char_groups` 源无分组）不再被误判为
  变更。回归：`TestImport_辅表为空不误判变更`。

### 阶段 C — 健壮性增强 — ✅ 已实施（2026.10.16.13）

- **C1 `Promote` 原子替换** ✅：`subscribe.writeFile` 统一为「`os.CreateTemp`
  同目录临时文件 → 写入 → `Sync` → `Chmod(0644)` → `Rename` 覆盖」。Stage /
  Promote / Abort / SaveLock / writeJSON 全部写入路径获得原子性，中断不再留半截
  生效文件。回归：`TestWriteFile_原子替换不留半截文件`（残留检查 + 权限归一，
  Windows 无 POSIX 权限位故跳过权限断言）。
- **C2 校验报告增强** ✅：`validate.Errors.Summarize(sampleN)` 按 (字段, 规则)
  聚合计数 + 前 N 条明细样例（顺序经 `sorted()` 稳定，可 diff）；`failValidate`
  改走聚合输出。回归：`TestErrors_Summarize聚合`（聚合计数、样例、稳定性、
  截断边界）。
- **C3 抽 `importXxx` 通用骨架** ✅：按「源结构 × 落库形态」归并两个骨架——
  `importStringSliceMaterial`（JSON 字符串数组 → 单列，覆盖 naming_gate /
  forbidden_combos）与 `importKindRowsMaterial`（多分类 JSON → (entry, kind)
  两列，覆盖 allowlist / compliance_redline）。四个 importer 只保留差异参数
  （版本串、校验函数、插入语句、错误标签 / read 闭包），样板约减 120 行。
  注册表分发与事务语义不变，既有测试全绿守护。

### 阶段 D — 可观测与回归固化 — ✅ 已实施（2026.10.16.13）

- **D1 CI 端到端断言** ✅：新增 `store_materials_idempotency_test.go`：
  ① 全量导入 + 二次导入走**正常指纹短路路径**，内容快照逐字节等价，
  且频率档派生列仍与 `name_frequency` 一致；
  ② 增量门控：仅改动单物料源文件时，只有该物料重灌（`Written == 1`），
  其余全部短路；
  ③ 辅表为空不误判变更（B3 回归）；④ 可选物料源缺失即跳过、不计失败。
- **D2 A2/A3 契约固化** ✅：阶段 A 实施时已落地——
  `TestImport_只导入指定物料并自动补齐依赖`（含康熙注入断言，证明不依赖回读）、
  `TestImport_全部短路时仍归一化档位`、`TestImport_仅namer变更时保留频率档位`、
  `TestImport_频率档位落库`。

### 阶段 P2-4（随 B/C 一并处理）

- **sha256 统一** ✅：`subscribe.HashBytes`/`HashFile` 委托 `materials/checksum`，
  全仓不再有两份指纹实现。
- **`ClassicalSc` → `ClassicalScore`** ✅：缩写命名对齐同族字段

## 五、验证状态与风险研判

- **当前绿度**：`go build ./...` ✅、`go vet` ✅、物料包测试 ✅；`schema/normalize/validate/checksum/review` 五包 **100%** 覆盖；据 `docs/32` M11，`e2e_check -strict` 双模式均 18/18。
- **风险研判**：P0 三项**不影响当前"已导入物料 + 双模式 e2e"的绿**，属于潜伏债务——一旦 `seedHanziData` 被误用、或导入顺序/`name_frequency` 源缺失，即暴露不一致。建议优先推进 **阶段 A**（收敛口径），再做 B/C 清理。
