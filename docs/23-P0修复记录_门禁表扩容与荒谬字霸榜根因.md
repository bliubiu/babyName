# P0 修复记录：质量门禁表扩容与荒谬字霸榜根因

> 版本：`2026.09.15.1`
> 上游审查：`docs/22-起名链路E2E巡检工具与质量防线审计.md` 第 2.3 节、第 3 节
> 工具：`backend/tools/gate_expand`、`backend/tools/gate_audit`、`backend/tools/e2e_check`

## 0. 一句话结论

**门禁表从 131 字扩容到 2990 字（并正式纳入版本管理），但真正修好 P0 的不是扩容——
实测证明黑名单扩容无法收敛 P0。** 根因在 `RateName` 的封顶豁免判据，必须同时修正。

## 1. 起因

上一轮 E2E 测得双名推荐榜 Top10 全部是「精选好字 + 任意生僻字」形态：

```
张沚明 张鲛慧 张唣明 张慧僰 张恃泽 张蚂泽 张浩荥 张噬鹏 张蚂宏 张蚂清
```

对照单名 Top10 正常（张明 张华 张海…），双名是问题高发区。
当时的判断是「好字信号覆盖不足 + 封顶豁免用 OR 逻辑 + 门禁表只有 131 字」三者叠加，
本次按「扩容门禁表」的指示实施，**实测后确认扩容单独不成立**（见第 4 节）。

## 2. 门禁表为什么会只剩 131 字（以及如何找回）

## 3. 扩容：旧表恢复 + 规则扩容（`tools/gate_expand`）

### 3.1 旧表恢复（`-recover aa024f4`）

1094 字表完整可寻回：commit `aa024f4` 的 Go 内嵌 `map[string]bool` 与后来外置的
JSON 是同一份数据（`7bfb8b9` 的注释佐证），用正则提取键名即可还原。
恢复后与现有 131 字比对：**现表是旧表的真子集**（`现表 ⊆ 旧表`，无独有条目），
即这次恢复是纯粹的正向补齐，不存在新老表冲突。

### 3.2 规则扩容（`isNamingIneligible`）

对《通用规范汉字表》8105 字逐一检查四个「证据维度」，全部落空即收进门禁表：

| 维度 | 判据 | 覆盖率 |
| ---- | ---- | ------ |
| a 真实人名用法 | `NameFreqTier > 0`（95.7 万条人名语料，2237 字） | 27.6% |
| b 人工寓意评分 | `positiveScore > 0` | 6.9% |
| c 策展好名认可 | `fate.IsCuratedChar` | 约 5.5% |
| d 典籍诗词出处 | `classics.HasPoetryChar` | 76.2% |

命中 **1975 字**（相对恢复后的基准表新增 1896 字）。

两条防误伤的保险：

- **吉祥部首豁免**：`王/玉` 部二级及以下的字豁免。美玉承载「君子比德于玉」意象，
  即便现代语料罕见也有命名价值（如 `瑄`）；三级过于生僻仍拦。
- **守护字表硬校验**：工具内置 115 个「无论如何不得入表」的优质字（含
  `若如然斯唯惟一三九百千万…` 与 `瑄翀婳愔` 等），命中即**拒绝写盘并退出 1**。
  实际上正是这道校验抓出了 `瑄` 的误伤，才有了上面的部首豁免。

## 4. ★ 关键实测：扩容本身修不好 P0

只上扩容（rater 不动）重启服务实测，双名 Top10：

```
张沚明 张鲛慧 张唣明 张珀晨 张慧僰 张恃泽 张浩荥 张噬鹏 张慧蚨 张飒呸
```

**沚/鲛/唣/僰/恃/荥/噬 一个都没少。** 原因：

1. 这批字**都查得到诗词出处**（`HasPoetryChar` 为真），因此规则不拦；
   实测 `沚/鲛/唣/僰/恃/荥/噬` 全部命中维度 d，这直接证明「诗词出处」没有区分力。
2. 即便把维度 d 也去掉（即「未在真实人名语料中出现」即拦），规则会一次命中
   **6816/8105 = 84%** 的字，连「彧」（荀彧）都会被误伤——那已经不是
   「无命名价值」，而是「现代不常用」了。

根因不在黑名单的覆盖面，而在：**评分体系对这些字没有任何负反馈**
（`positiveScore=0` 不产生惩罚），而**封顶豁免只要一个字达标就整组放行**。
只要这两条成立，榜单只会「换一批面孔」，这正是历史上 40+ 轮打不完的机制。

## 5. 真正的修复：封顶豁免加前置条件（`rater.go`）

```go
// 修复前：任一字是精选好字 → 整组豁免四维封顶
premiumChar := (IsCurated1 && ps1 >= 90) || (IsCurated2 && ps2 >= 90)

// 修复后：精选好字仍要，但两个字都必须具备「命名依据」
premium := (candidate.IsCurated1 && candidate.PositiveScore1 >= 90) ||
	(candidate.IsCurated2 && candidate.PositiveScore2 >= 90)
if !premium {
	return true // 封顶
}
return !hasNamingEvidence(IsCurated1, ps1, tier1) || !hasNamingEvidence(IsCurated2, ps2, tier2)
```

`hasNamingEvidence` = 寓意评分 > 0 ∨ 策展分类字 ∨ 出现在 95.7 万人名语料中。

设计要点：

- 判据是「**有没有依据**」而非「好不好」——不参与打分，只决定一个字有没有资格
  参与「豁免封顶」的组队，避免动到既有评分权重与分数标定。
- 保留多样性：两个有依据的字搭配精选好字仍可豁免（有依据的字约 2500 个），
  不做成「两字都必须精选好字」的 AND，否则榜单会退化成少量好字的排列组合。
- 单一判据函数 `nonCuratedCapApplies` 由 `RateName` 与 `RateNameScore` 共用，
  两条路径总分依旧逐位一致。

## 6. 顺带修掉的两个既有缺陷

### 6.1 出典回填未清空 `PoetrySource`（`fate_name_service.go`）

`enrichPoetrySource` / `enrichPoetryForName` 的「索引未命中」分支，注释写的是
「原 PoetrySource 留空，PoetrySentence 兜底引擎原句」，但代码只把原句**复制**到
`PoetrySentence`，没有清空 `PoetrySource`。而调用方会先用引擎格式化原句（`「…」`）
预填 `PoetrySource`，于是前端会把原句渲染成《「睿而爲愚者也」》——出处位置出现
引号包着的句子。名称排序变化让这类名字浮上榜单，`TestGenerate_PoetryBackfill`
随即报错暴露了它。现按注释的既定语义补上清空（分析路径与生成路径一并修正）。

## 7. 回归护栏

- `TestNonCuratedCapRequiresNamingEvidence`：6 组判据（好字+无依据字必须封顶、
  好字+人名语料/策展/寓意评分豁免、策展白名单优先豁免、单名不封顶）。
- `TestHasNamingEvidence`：命名依据判据真值表。
- `tools/e2e_check` 的 P0 探测器口径同步改为「无命名依据字」而非「无 positiveScore」——
  后者会误报（`珀/赟/茗/诗` 本就没有寓意评分却完全可用），前者才是荒谬字的成因。
- `tools/gate_expand` 内置守护字硬校验：优质字被误伤即拒绝写盘。
