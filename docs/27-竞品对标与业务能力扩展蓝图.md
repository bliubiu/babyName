## 0. 本轮的定位与三处纠正

`docs/15` / `docs/18` 写于 2026-07 / 2026-08，其结论与当前代码已经漂移；其中还有一条建议与本项目的硬约束直接冲突。本蓝图先纠正，再给可执行清单。

| 前序结论 | 现状核对结果 | 本轮处置 |
| --- | --- | --- |
| `docs/18` 建议「**必须补充五格数理 + 三才配置**，fate / 美名腾 / 云美名都有，是基础门槛」 | 与 `AGENTS.md`「**禁用熊崎五格数理（三才五格）**，必须严格遵循应用传统易学理论」直接冲突 | ❌ **明确排除**。三才本身保留（三才出自《系辞下》《说卦传》，是先秦原生概念），但三才五格的**81 数吉凶打分**不引入 |
| `docs/18` 认为本项目「**缺少文字解读，用户不知道"为什么好"**」 | 引擎侧其实**已经产出**每维度的依据文字（`fate.NameRating.Detail` → `Score.ScoreDetails`），前端 `NameCard` / `NameDetail` **也已经写好了 `score_detail` 渲染分支**——只是 `/names/generate` 这条链路把依据文字丢掉了，分支永不执行 | ✅ 本轮已修（§5）。这不是"缺能力"，是"能力没接出来" |
| `docs/18` 认为「评分维度 8 维 > fate 5 维 > 美名腾 6 维，维度最多即优势」 | 维度数量不是用户可感知的差异；**能否解释**才是 | 度量口径改为「依据文字覆盖率」而非维度数 |

同时补一条前序文档都没提、但本轮核对中最扎眼的结论：

> **后端 30 个接口中，前端真正有页面在用的只有 9 个。** 大量已实现、已注册、已测试的能力（八维评分依据、八字分析、易经卦象、生肖宜忌、4 类人名语料统计、真实 PDF 报告）没有入口。**这是当前性价比最高的「业务能力扩展」来源**——不需要写新算法，只需要把已有能力接到界面上。

## 1. 市场与竞品现状（2026-09）

### 1.1 竞争格局

| 阵营 | 代表 | 2026 年的打法 |
| --- | --- | --- |
| 传统起名站 / App | 美名腾、起名网、起名通、林墨轩、灵机妙算 | 功能堆叠 + 大师人工服务变现；起名通把「大数据避重名 / 避网红字」做成核心卖点 |
| AI 新锐 | goodname.ai、千千起名、DeepSeek 系命理 App | 「AI + 国学双引擎」，强调**真太阳时 + 经纬度校准**、**谐音风险筛查**、**每字适配命格的解释** |
| 开源 | babyname/fate v4.2.0、gushi_namer（Chinese-Names-Corpus） | 技术透明、免费、单二进制；fate 迭代到 v4 并补齐了异步任务与探索模式 |
| 内容 / 流量 | 诗词起名小程序、姓名测算工具站 | 靠诗词库撑内容，命理深度弱 |

### 1.2 竞品关键能力（对本项目有借鉴价值的）

| 竞品 | 值得借鉴的点 |
| --- | --- |
| **babyname/fate v4.2.0**（技术栈与本项目最接近） | ① **双算法喜用神可切换**（平衡用神法 / 格局用神法）；② **异步任务 + task_id 轮询进度**（`/api/generate` → `/api/task/:id` → `/api/names/:taskId`），而不是同步等一个长请求；③ **探索模式 `Explore(N, filter)`**：在 Top-N 之外随机采样出"另一批"，天然解决"看来看去就这几个"；④ 候选名册表格/卡片双视图；⑤ CLI 可用 |
| **美名腾** | 六度空间逐维**文字推导**（每一步都写清为什么）；App + Web 双端 |
| **起名通** | 用真实人名语料做**重名率 / 网红字规避**，把"社会学数据"做成卖点 |
| **千千起名** | 真太阳时 + 经纬度；**谐音风险筛查与生僻字风险提示**（其数据称该功能使用率同比 +47%）；明示"拒绝粗暴缺啥补字，区分五行缺失与五行过旺" |
| **goodname.ai** | 20+ 参数输入；典籍溯源；**智能校验**（生僻字 / 禁用词 / 名人重名） |

### 1.3 2026 用户需求迁移（行业公开数据 + 测评共性）

1. **可解释性 > 玄学分数**：用户反感"动辄 98 分"的模板分；要的是"这个字为什么适合我的孩子"。
2. **风险提示成为刚需**：谐音风险、生僻字风险、多音字、户籍登记友好度、网红字撞名——使用率显著上升。
3. **双重筛选常态化**：约 62% 的用户同时开启「典籍来源」与「生辰适配」。
4. **测名是最大的未满足入口**：用户在网上搜集几十上百个候选名，**约 70% 会在测名环节被筛掉**。也就是说用户的真实动线是"**先攒名字，再逐个筛**"，而不是"输入生辰等系统给名字"。
5. **反感套路**：虚假免费、核心功能付费墙、广告弹窗。本项目「开源 + 免费 + 离线单二进制」在这一项上是结构性优势。
6. **命理深度不能靠"缺啥补字"**：要区分「缺失」与「过旺」，要有调候意识（本项目已具备月令加权、真太阳时、纳音立春校正等）。

## 4. 借鉴清单（落到文件级）

### 4.1 立即可做（把已有能力接出来，零新算法）

| # | 借鉴来源 | 做什么 | 落点 | 为什么高 ROI |
| --- | --- | --- | --- | --- |
| A1 | 千千 / 美名腾 | **新增「测名」入口**：输入任意姓名 + 生辰 → 完整报告（八维依据 + 出典 + 卦象 + 风险清单） | 见下方「⚠ 实现前提」 | 用户真实动线是"先攒名字再筛"，70% 的候选名会被筛掉。**这是全竞品都有、本项目唯一完全缺失的功能形态** |

> **⚠ A1 的实现前提（已核对代码，勿低估）**
>
> `fate.RateName(candidate *NameCandidate, fateData *FateData, raters []Rater) NameScore` 确实是导出的、可直接复用；但两处输入都不好拿：
>
> 1. **`NameCandidate` 有 20+ 字段**（逐字拼音 / 五行 / 简体·康熙笔画 / 字义 / 部首 / 常用等级 / 人名频率档位 / `PositiveScore` / 策展标记 / 字义画像 / 姓氏拼音），目前**只在引擎内部枚举候选时组装**，没有任何导出入口。要支持"任意名字打分"，必须先从引擎抽出「给定姓名 → NameCandidate」的装配函数（否则测出来的分会与结果页同名的分不一致，反而制造新的双口径问题）。
> 2. **`FateData`** 由 `BaziAnalyzer` 接口的 `Analyze(born, gender) (*FateData, error)` 产出，需要把它作为依赖注入 `NameService` 才能在测名路径复用同一份命理数据。
>
> 结论：A1 的工作量是**中等偏上**（不是"接个接口"），但收益是**红色缺口**。建议做法是先在 `domain/fate` 增加一个导出函数
> `RateGivenName(surname, given string, fateData *FateData, provider CharacterProvider, raters []Rater) (NameCandidate, NameScore)`
> ——让"结果页的名字"与"测名页的名字"共用同一条评分装配链，再在其上包一层服务与接口。这也是本项目"双链路口径必须一致"的既定教训（见 `docs/24` P2-6）的直接应用。
| A2 | 千千（使用率 +47%） | **风险体检清单**：谐音 / 生僻字 / 多音字 / 负面联想 / 网红字撞名，逐项给「通过 / 提示 / 不通过」+ 人话解释 | 引擎侧 `Homophone` / `IsBadCombo` / 门禁表 / `name_frequency` 已有判据，需要的是**聚合为结构化清单**并透出 | 判据全在，只差一个出口 |
| A3 | 起名通 | **重名热度接入**：结果页每个名字显示"全国约 X 人同名 / 热度档位"；新增「热度榜」二级页 | 后端 `/namestats/*`（8 条）**已实现且已测试**；前端只需接入 | 后端零改动 |
| A4 | — | **字义解释接入**：逐字展示 `word.json` 字义（16,142 条现成素材） | 新增 `GET /api/v1/characters/meaning/:char`，复用 `word.json` | 素材现成，"家长能看懂每个字"是核心诉求 |
| A5 | 美名腾 | **真实 PDF 报告入口**：结果页"导出报告"按钮调 `/report/pdf` | 后端 `docs/25` 已实现；前端加按钮 | 后端零改动，直接把已投入的实现变现 |

## 6. 建议的后续批次

### 批次二（推荐，1-2 轮迭代）：把"测名 + 风险体检"做出来

对应 §4.1 的 A1 + A2 + A4。这是竞品矩阵里**唯一的红色缺口**，且复用现有引擎与数据，不需要新算法。

验收标准：
1. `POST /api/v1/names/evaluate` 接受「姓名 + 生辰」，返回与 `/generate/analysis` **同构**的名字分析（八维分数 + 依据文字 + 出典 + 卦象）。
2. 风险清单结构化输出，每项含 `level`（pass / warn / fail）+ 中文说明；至少覆盖：谐音、生僻字（三级字表）、多音字、负面联想、门禁字、撞名热度。
3. 前端新增 `/evaluate` 页，与结果页共用 `NameDetail` 组件（`score_detail` 已支持）。
4. 单元测试覆盖：风险清单各档位判定、等级边界、空输入、未收录字。

### 批次三：交互与体验

对应 A3 + A5 + B1 + B2：结果页接入重名热度与 PDF 导出入口；异步任务 + 进度；探索模式「换一批」。

验收标准：长任务不再依赖 30s 超时兜底；「换一批」返回的结果与 Top-N 交集受控且可复现（同一 seed 可复现）。

### 批次四：性能与一致性

对应 B5 + B6 + `docs/24` P2-6（双链路喜用神口径统一）。以 `tools/e2e_check -strict` 接入 CI 作为回归门禁。

## 7. 度量口径建议

前序文档用「评分维度数量」证明领先，这个口径对用户无感。建议改用：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **依据文字覆盖率** | 结果页中「至少一个维度带依据文字」的名字占比 | 100%（本轮 S1 后应达成） |
| **风险提示覆盖率** | 输出名字中带完整风险清单的占比 | 批次二后 100% |
| 单请求 p95 延迟 | `tools/e2e_check` 采集 | 双名 < 1s |
| 无依据字上榜率 | `tools/e2e_check` P0 探测项 | 0%（已有门禁） |
| 接口利用率 | 前端实际调用的接口 / 后端已实现接口 | 9/30 → 批次二后 ≥ 15/30 |

## 8. 一句话结论

本项目的算法与数据底子（真太阳时、月令加权喜用神、2990 字质量门禁、95.7 万条人名语料、6 类诗文库、离线单二进制）在开源同类里属于上乘，**真正落后的是"把能力讲给用户听"这一段**：评分依据、字义、语料统计、PDF 报告都已实现却没有出口，而"测名 + 风险体检"这个全竞品标配的入口完全缺失。因此后续投入的优先级应该是「**接出口 > 补缺口 > 加新算法**」。
