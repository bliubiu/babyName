## 二、P2 处置

### B3 · 除夕硬编码腊月三十

- **处置**：两段逐字重复的 365 次逐日轮询合并为单次 `findNextHoliday`，同时产出天数与名称；`GetHoliday` 增加按日期缓存（返回副本、超 8192 条整体重建）。
- **验证**：`holiday_perf_test.go` 以「保留原双循环的参考实现」逐一对拍，确保合并未改变任一语义；另断言缓存不被调用方改写污染、上界生效。

### B5 · 黄历年月切换日期溢出
- **处置**：新增 `frontend/src/app/huangli/dateUtils.ts` 的 `buildClampedDate`，把「日」钳制到目标月最后一天，替换两处 `new Date(...)` 构造。
- **验证**：`dateUtils.test.ts` 9 例，覆盖闰年、平年 2 月、大小月、跨年及全月遍历不变式。

### B6 · 历史/收藏无分页上限
- **处置**：统一分页查询，`maxPageSize = 100`，非法分页 400；`/favorites` 返回分页结构。
- **验证**：`favorite_service`、`history_handler` 相关测试；前端类型契约同步。

### B7 · 异步任务无上限堆积 OOM
- **处置**：运行信号量容量 4；满载 `Submit` 返回 `ErrTooManyTasks`（handler → 503）；淘汰与 TTL 取消运行中任务并标记 `evicted`；取消后忽略进度、不回填结果；`defer` 释放槽位。
- **验证**：`task_service_test.go` 覆盖提交拒绝、淘汰取消、TTL、完成态不被取消、槽位归还、取消无结果。

### B8 · SQL 故障伪装成「无结果」
- **处置**：`SearchHanziByFilter` 全链路返回 `error`；查询成功但结果为空与查询失败可区分；失败时可降级 Go 内存过滤。
- **验证**：`adapters_fallback_test.go`、SQLite `filter_integration_test.go`。

### B9 · 全局字库并发无锁
- **处置**：`ApplyWuxingOverrides`/`mergeKangxiStrokes` 自持 `mu` 写锁；`namerMu` 与 `mu` 锁序固定；读侧统一迁移到 `GetHanzi`/`GetNamerChar`。
- **验证**：`hanzi/concurrency_test.go`。**实测反证**：临时移除写锁后，`fatal error: concurrent map writes` 稳定复现；恢复后通过。
- **说明**：`LoadFromJSON` 仍为「局部构建 → 锁内合并 → 锁外应用覆盖」，即非整体替换、旧键保留。语义是否改为整体替换待确认（不影响当前并发安全）。

### B10 · `ShiCiExtracted` 并发读写
- **处置**：新增 `copyExtracted`（读锁 + 快照复制），`loader.go`/`bigram.go`/`poetry.go`/`poetry_index.go` 全部读取点改走它。
- **验证**：`go test ./internal/domain/classics/` 通过（含既有诗词索引测试）。

### B11 · `Reload()` 自死锁
- **处置**：`Reload` 不再持锁调用 `Load`；改为「清空索引临界区 → 释放 → `Load`」。热更新期间存在极短空索引窗口，已在注释中说明取舍。

### B12 · 生产配置链断裂（含补正）
- **原始问题**：`COPY config/` 路径不存在（构建必失败）；viper 搜索路径不含 `/app/config`；默认 `host: localhost` 容器内只绑回环（nginx 502）；DB 相对路径不在持久卷（重建丢数据）；`PORT`/`LOG_LEVEL` 与 `NAME_` 前缀不匹配。
- **补正发现**：
  1. 修正 COPY 路径后，compose 挂载宿主目录到 `/app/config` 仍会**遮蔽**镜像内配置 → 新部署配置缺失、viper 全量回落默认值；

### IP 直接访问的部署要点（2026.10.03 实测）

- **`server_name` 必须包含访问用的 IP/域名**（部署侧修改，仓库保留占位域名）：
  `sed -i "s/server_name your-domain.com www.your-domain.com;/server_name your-domain.com www.your-domain.com <IP>;/g" nginx/nginx.conf`。
  否则非配置域名的请求全部落入默认服务器（`/healthz` 之外一律 444）——
  浏览器表现为 ERR_EMPTY_RESPONSE。
- **bind-mount 单文件的 inode 陷阱**：`sed -i` 通过「替换文件」实现，容器挂载的
  仍是旧 inode——改完 nginx.conf 必须 `docker compose restart nginx`（reload 无效），
  并用 `docker exec namer-nginx grep … /etc/nginx/nginx.conf` 验证容器内文件确实已变。
- 访问路径实测（外部机器）：`http://IP/` → 301 → `https://IP/` → 前端页面 200；
  生成 API 经 https 200（薇澈 79 / 澈薇 78.6 / 梅璟 76.3）。浏览器首访会提示
  自签名证书不可信（测试证书 CN=test.local），点「高级 → 继续前往」；消除告警
  需正式域名走 certbot 签发并替换 /data/certbot 下证书三件套。
- 从 Windows 控制台用 curl 测中文请求体时注意 GBK 编码污染（表现为后端 400
  「姓氏只能包含中文字符」——校验器正确工作），应使用 UTF-8 文件 + `--data-binary @file`。

## 九、E2E 吞吐判据改造 + B14 决策关闭（2026.10.02，docs/28 §8.5 遗留）

### 1. 吞吐判据改造（tools/e2e_check 第 6 节）

**旧判据缺陷**（docs/28 §8.5.1 推导）：加速比 ≈ NumCPU/f（f=枚举段占服务时长比例），
与并行调度健康度无关——串行路径优化越好比值越低（假阳性），超订+慢串行段反而
可能达标（假阴性）。9.25 那轮 16/17 的误报即此。

**新判据**（替换 `speedup < 1.5` 单一判定）：
1. **并发吞吐 ≥ 串行吞吐**——并行至少不比串行慢；
2. **并发 p95 ≤ 串行时长 × 12**——防排队延迟爆炸。

p95 阈值校准依据：worker 钳制 NumCPU + 低枚举占比下，p95 膨胀 ≈
(并发/NumCPU)×(1/f)；本机三轮实测 8-9×（docs/28 §6 中位 6.9s / 串行 0.87s
同构），12× 为包络上限——OOM/无界排队类爆炸通常 30×+，仍会被抓住。
加速比降级为信息展示。检查项 17 → **18** 项。

**实测**（本机 HEAD，-strict）：**18/18 通过**——并发吞吐 2.27 ≥ 串行 1.35 ✓、
p95 7.10s ≤ 0.741×12 ✓、加速比 1.68×（旧判据阈值边缘，改造后不再构成误报风险）。
