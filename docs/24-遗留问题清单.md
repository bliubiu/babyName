## P1

### 1. ✅ 已修复（`2026.09.15.3`）`RequestTimeout` 中间件在超时后与 gin 上下文复用竞争

`backend/internal/infrastructure/middleware/middleware.go:367-397`（服务端 30s 超时，
见 `cmd/server/main.go:335`）

```go
done := make(chan struct{})
go func() { c.Next(); close(done) }()   // ① 在 goroutine 里跑后续 handler
select {
case <-done:
case <-ctx.Done():
    c.AbortWithStatusJSON(503, ...)      // ② 超时分支直接返回
}
```

超时分支返回后，gin 会把 `*gin.Context` 放回 `sync.Pool` 复用，而 ① 的 goroutine
**仍在写 `c.Writer`**；`defer cancel()` 也会让该 goroutine 之后的写操作落在已取消的上下文上。
后果不是「简单超时」，而是**跨请求串号/响应体被两个请求交替写入**。

- 触发条件：单请求超过 30s。当前正常耗时 0.5~2.4s，但并发超订下已观测到 2.4s，
  且无全局超时兜底。

**修复方案**（`middleware.go` + `fate_name_service.go` + `name_service.go` + `name_handler.go`）：

1. **不再 fork goroutine**：`c.Next()` 改回串行执行。gin 的 `Context` 不支持并发使用，
   想在中间件里"强行中断" handler 就无法避免上下文复用竞争，只能让超时通过
   `ctx` 传播给业务代码。
2. **补 503**：处理链返回后，若 `ctx.Err() == context.DeadlineExceeded` 且一个字都没写出，
   由中间件补 503（此时仍在 gin 的串行流程内，写响应是安全的）。
3. **★ 顺带修掉一个更严重的问题：超时时返回被截断的 200**。引擎各分片在 `ctx.Done`
   后提前退出、`session.Wait()` 仍正常返回，而服务层此前不检查 `ctx.Err()`——
   实测「给一个已过期的 deadline，`GenerateWithAnalysis` 返回成功结果」。
   现在服务层显式把 ctx 错误透出，handler 用 `errors.Is(err, context.DeadlineExceeded)`
   映射为 **503**（此前一律 500，前端无法区分「可重试」与「服务异常」）。
4. **残留限制**（已写入代码注释）：完全不理会 ctx 的 handler 仍会阻塞到
   `http.Server` 的 `WriteTimeout`，中间件无法安全地强制中断它——这是 gin 上下文体用池
   模型的固有约束。

**回归护栏**：`request_timeout_test.go` 7 个用例（正常透传 / deadline 且未写响应补 503 /
**响应不得被拼接** / 中间件返回晚于 handler 结束 / `timeout<=0` 不干预 / deadline 传下游 /
上游取消不误报 503）；`TestGenerateWithAnalysisDeadlineExceeded` 断言超时不再返回成功。
前两个用例在旧实现上会失败（已验证）。

### 9. ✅ 已修复（`2026.09.18.0`）`close(shiciReady)` 未 `defer` → panic 后所有诗词相关请求永久阻塞

> 修复方式：加载协程改为 `runShiCiLoad(loader, ready)`——`recover` + `defer close(ready)`
> 双保险（`recover` 保证 panic 不打崩进程、`close` 保证等待方一定被唤醒）；
> `ensureShiCiLoaded` 改为 `waitShiCiLoaded` 有界等待（30s 超时即降级为无诗词共现数据并告警）。
> loader 以参数注入，使「panic 也会关闭通道」这条不变量可被确定性测试覆盖。
> 回归护栏：`shici_ready_test.go`（7 用例）。

`backend/internal/domain/classics/classic_loader.go:126-138`

```go
go func() {
    if err := loadShiCiFromJSON(dataDir); err != nil { logger.Error(...) }
    close(shiciReady)          // 若上面 panic，这里永不执行
}()
```

`ensureShiCiLoaded()` 是 `<-shiciReady` 的**无超时死等**，一旦该 goroutine panic，
所有依赖诗词的请求会全部挂死（而不是报错）。这也是「跨进程冷启动结果有差异」的可疑源头之一。

- 建议：`defer close(shiciReady)`，并给 `ensureShiCiLoaded` 加超时。
