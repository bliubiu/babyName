# 起名链路 E2E 巡检工具与质量防线审计

> 版本：`2026.09.15.0`
> 相关：`docs/19-起名服务候选池到生成管线深度审查报告.md`、`docs/21-系统审查与修复记录.md`
> 工具：`backend/tools/e2e_check`、`backend/tools/gate_audit`

## 0. 为什么要有这两个工具

起名链路的输出质量由**多层防线**共同决定（笔画/生僻字/性别/硬负面语义/门禁表/组合禁忌/
共现白名单/四维封顶…），任何一层被绕过或失效，表现都是「榜上出现荒谬字」，
但排查时很难定位到底是哪一层漏了。历史上已出现过 11 轮「荒谬字换面孔霸榜」。

因此把两件事固化成可重复执行的 Go 工具，取代一次性脚本：

| 工具 | 解决的问题 | 依赖 |
| ---- | ---------- | ---- |
| `tools/e2e_check` | 服务启动后端到端巡检：耗时、用字质量、参数生效性、双路径一致性、可复现性、并发 | 仅标准库，需服务在跑 |
| `tools/gate_audit` | 质量门禁表（`data/naming_quality.json`）覆盖审计：哪些字是它唯一挡住的、移除会怎样 | 仅标准库 + 内部包，不需服务 |

两者都是**只读**的：只发 HTTP 请求、只读 `data/` 目录，不写入任何项目数据。

## 1. 用法

```bash
# 前置：启动服务
cd backend && go build -o namer-server.exe ./cmd/server && ./namer-server.exe

# 1) E2E 巡检（默认 127.0.0.1:8080）
cd backend && go run ./tools/e2e_check
go run ./tools/e2e_check -concurrency 32 -strict   # -strict：发现问题以退出码 1 结束，便于 CI
go run ./tools/e2e_check -host localhost:8080      # 注意：Windows 上 localhost 会先试 ::1，可能多出约 2s

# 2) 门禁表覆盖审计（不需服务）
go run ./tools/gate_audit
go run ./tools/gate_audit -static-only             # 跳过生成对照，仅静态分析
```

两个工具都会自动定位数据目录（依次尝试 `-data`、`data`、`../data`、`../../data`），
因此无论从 `backend/` 还是工具自身目录启动都能工作。

> 旧的 `backend/scripts/e2e_name_check.py` 已删除，由 `tools/e2e_check` 取代（不再依赖外部 Python）。

### 2.3 ★1 双名榜被「无正向信号字」稀释（P0，已于 `2026.09.15.1` 修复）

> 修复过程与实测数据见 `docs/23-P0修复记录_门禁表扩容与荒谬字霸榜根因.md`。
> **关键结论：门禁表扩容单独修不好 P0**——实测扩容后荒谬字一个没少（沚/鲛/唣/僰/恃/荥/噬
> 都查得到诗词出处，规则不拦），根因在 `RateName` 的封顶豁免判据，两者必须同时修正。
> 修复后的 Top10：`张珀熙 张慧茗 张珀诗 张茗浩 张赟慧 张珀宏 张珀明 张珀渊 张珀辉 张珀泽`。

实测双名 Top10：

```
张沚明 张鲛慧 张唣明 张慧僰 张恃泽 张蚂泽 张浩荥 张噬鹏 张蚂宏 张蚂清
```

对照单名 Top10 正常：`张明 张华 张海 张红 张鹏 张宏 张泽 张慧 张平 张云`。

因果链：

1. **好字信号极稀疏**：8105 字中仅 **563 字**有 `positiveScore`，`ps≥90` 仅 125 字。
2. **`positiveScore=0` 不产生任何惩罚**——它只被 `charPotentialScore`（早停启发式）消费。
   于是「蚂」与「清」在评分上**完全等价**。
3. **封顶豁免用的是「或」**（`rater.go`）：

   ```go
   premiumChar := (IsCurated1 && ps1 >= 90) || (IsCurated2 && ps2 >= 90)
   ```

   只要一个字达标，整组即免于「文化/音韵/生肖/三才」四维封顶 75。
4. 结果：**含 1 个精选好字 + 1 个任意垃圾字**的组合免于封顶，纯垃圾组合被压到 ≤78 分，
   Top50 因此 100% 含无信号字。

实际采用的修法（`2026.09.15.1`）：保留「精选好字」作为豁免的**必要**条件，
但追加前置判据——**两个字都必须具备命名依据**（寓意评分 / 策展分类 / 真实人名语料）。
判据是「有没有依据」而非「好不好」，不参与打分，因此不动既有权重与分数标定；
同时不做成「两字都须精选好字」的严格 AND，以免榜单退化为少量好字的排列组合。

### 2.4 ★2 两条链路喜用神互相矛盾（P1）

同一人、同一出生时间：

| 端点 | 喜用神 |
| ---- | ------ |
| `/api/v1/names/generate/analysis` | `[水]`（fate 引擎） |
| `/api/v1/names/generate` | `[木 水 金]`（经典 `BaziAdapter`） |

两条链路跑的是**两套喜用神算法**，API 给出的结论直接冲突，前端会呈现「同一个人两个答案」。

### 2.5 ★3 双路径响应结构分裂（P1）

`names[0]` 字段差异（`/generate` 相对 `/analysis`）：

- 仅 `/analysis` 有：`score_detail`、`sancai`、`xiyongshen`、`zodiac_match`、
  `meaning_detail`、`name_db_score/source`、`nayin_analysis`、`yinyun_analysis`、`bazi_analysis`、`recommendations`
- 仅 `/generate` 有：`id`、`generation`、`huangli`、`meaning`、`nayin`、`reasons`、`xiang`、`yinyun`、`bazi_score_detail`

两个端点的 `bazi` 字段集是一致的（21 个），但名字条目结构不同，前端需写两套渲染逻辑。

### 2.6 并发超订（P2）

每个请求内部固定用 `runtime.NumCPU()`（16）个 worker 分片。并发一上来，worker 数成倍超过核数：

| 并发 | 单请求中位 | 放大系数 | 吞吐 |
| ---- | ---------- | -------- | ---- |
| 1（串行基线） | 0.53 s | 1.0× | 1.9 req/s |
| 4 | 0.79 s | 1.4× | 4.8 req/s |
| 8 | 1.26 s | 2.4× | 6.3 req/s |
| 16 | 2.3~3.7 s | ~5× | 4~7 req/s |

吞吐在 8 并发附近见顶，之后单请求耗时线性恶化。建议按在飞请求数动态限制 worker 总数。

## 3. 门禁表能否移除（`data/naming_quality.json`）

**结论：不能移除。** 它是当前**唯一**挡住文言虚词/排行字/口语物名/数字量词的防线；
真正的问题是它**覆盖严重不足**。

本节数据为 131 字表审计时的原始快照。该表已于 `2026.09.15.1` 扩容到 **2990 字**
（自 git `aa024f4` 恢复历史 1094 字表 + `tools/gate_expand` 规则扩容 1896 字），
并纳入版本管理，见 `docs/23`。扩容后的关键数字：
门禁表 2990 字中 **1775 字只有它挡得住**（其余 1215 字已被其他防线覆盖）；
双名字源池 5558 → **3778 字**，组合规模 3089 万 → **1427 万对**。

### A. 静态覆盖：113/131 字只有它在挡（131 字表时期）

`filter` 链输出候选池 **5558 字**（双名路径在候选池阶段**不**应用门禁表，见 `engine.go` 注释）。
把门禁表 131 字逐字过一遍其他防线：

| 分类 | 字数 | 说明 |
| ---- | ---- | ---- |
| ★ 仅靠门禁表拦截 | **113** | 已通过 filter 链进入候选池，移除即可被使用 |
| 已被 `IsNegative` 标记覆盖 | 1 | 二 |
| 已被 filter 链挡下 | 17 | 七乳兮半咽嚼壬彼懈拧撒既熏纽膀踢踩 |

即：**113 字（之/乎/也/与/五/六/十/四/仲/伯/叔/季…）的唯一拦截者就是这张表。**

### B. 动态对照：移除后的实际影响（131 字表时期）

分别用「启用门禁」与「门禁置空」（`LoadNamingQualityFromJSON` 指向不存在目录即降级为空表）
跑完整生成：

| 路径 | 已评分组合数 | 门禁字是否进入 Top50 | Top50 差异 |
| ---- | ------------ | -------------------- | ---------- |
| 双名 启用门禁 | 94,164 | 无 | — |
| 双名 门禁置空 | 98,311 | 无 | 8 个（榜单改变但未放进门禁字） |
| 单名 启用门禁 | 5,357 | 无 | — |
| 单名 门禁置空 | 5,470 | **有：伯** | 7 个 |

两点结论：

1. **双名路径**：门禁字的评分本就极低，不加门禁也上不了榜——所以门禁表在双名上的作用是
   「缩小搜索空间」（−4% 已评分组合数）而非「拦住上榜」。**但榜单确实变了**（8/50），
   说明它不是无副作用的白名单装饰。
2. **单名路径**：移除后「伯」直接进入 Top50——**有实锤回归**。单名的候选池只有 ~1100 字，
   门禁表在这里承担真实过滤职责。

### C. 替代方案（黑名单 → 正向信号准入）不可行

若改成「只有带正向信号的字才准入」：

| 指标 | 数值 |
| ---- | ---- |
| 当前候选池 | 5,558 字 |
| 其中带正向信号（策展字 或 `positiveScore>0`） | **386 字** |
| 无任何正向信号 | 5,172 字（**93%**） |
| 双名组合规模 | 现池 30,891,364 对 → 准入集 **148,996 对** |

准入集只有 386 字，会重新触发历史问题——
`engine.go` 注释明确记录过：「曾用『人工寓意评分≥85』作为唯一字源门槛，
把候选池收窄到 200-360 字，导致多次生成名字高度近似」。

**所以正确方向不是删表，而是补信号**：扩大 `positiveScore` / 策展覆盖，
让「好字」与「无信号字」在评分上真正可分，门禁表退化为兜底而非主力。
