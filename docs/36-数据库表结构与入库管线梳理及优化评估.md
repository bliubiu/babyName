# 起名项目 SQLite 数据库表结构与入库管线梳理及优化评估

> 梳理日期：2026-10-21
> 范围：`backend/namer.db` 与根目录 `namer.db` 两张 SQLite 库、物料注册表 `internal/materials/schema`、导入实现 `internal/infrastructure/database/sqlite/store_materials_import.go`（含 classics/kangxi 分支）。
> 目的：① 理清既有表结构与索引；② 理清 JSON→表 入库管线；③ 评估并给出表结构与数据的整理优化建议。

---

## 0. 概览与一句话结论

项目当前存在**两份** SQLite 库，结构已分叉：

| 库文件 | 大小 | 表数 | 残留旧表 | 运行期数据 |
|---|---|---|---|---|
| `backend/namer.db` | 25.97 MB | 24 | `words`(14809行)、`data_meta`(2行) | curated_names=59、gate_review=7、history=3 |
| 根目录 `namer.db` | 23.91 MB | 22 | 无 | curated_names=52、gate_review=0、history=7 |

- 运行服务默认 `database.path = "namer.db"`（相对 cwd，见 `config.go`）；本地以 `backend/` 为工作目录启动时实际加载 `backend/namer.db`。根目录那份应是某次在仓库根执行 `materials import` 产生的**游离副本**。
- 整体上物料模型设计**成熟且自洽**：物料表与运营表分离、单事务全量重建+指纹短路、派生列单一真源、反规范化已收敛。主要问题集中在**双库分叉与孤儿表残留**，其次为若干**数据覆盖缺口**与**少量索引缺失**。

### 1.2 核心表字段（要点）

**`hanzi_data`（26 列）**：`char` PK；基础信息 `pinyin/strokes/kangxi_strokes/radical/meaning/wuxing/gender/level/tone`；派生/评分 `name_freq_tier/usage_level/positive_score/phonetic_score/modern_score/classical_score/curation_level/name_penalty`；布尔 `is_polyphonic/is_rare/is_negative`；标签 JSON `gender_tags/style_tags/pair_blacklist/naming_categories`；`updated_at`。

> 字段已在 DDL 中集中定义，并通过 `migrateHanziDataColumns` 增量补列；新增列必须同时登记到补列清单，作为防 schema 漂移的单一真源。

**`name_bigram`**：`key`(PK,=char1+char2)、`char1`、`char2`、`count`、`rank`、`tier`。**仅有主键自动索引，无 (char1,char2) 复合索引**。

**`classics_*` 四表**：`classics_extracts` 在 docs/34 阶段 E-A 已去除 `pinyin/meaning/wuxing/gender` 冗余列（这些属性运行期按 char 回查 `hanzi_data`）；`classics_poem_entries` 的 `content/tags` 是纯 JSON 文本，未建任何二级索引。

### 1.3 索引现状

已建索引（覆盖良好）：`hanzi_data` 5 个单列（wuxing/strokes/pinyin/level/gender）、`classics_books(file_name)`、`classics_sections(book_id)`、`favorites(surname,given_name)`、`gate_review`(唯一键 name+layer+category+hit_value + status)、`history(created_at)`、`name_requests(hash)`、`name_feedback(request_id)`。

**缺口**：
- `name_bigram`：仅主键索引。若需按首字 `char1` 检索双名（`WHERE char1=?`）会全表扫描 12.5 万行。
- `classics_poem_entries`：仅主键 `id`。按 `source/title/author/dynasty` 检索或全文 LIKE 均全表扫描 1.2 万行（当前规模可接受，但检索需求若增强需补索引）。

## 2. JSON→SQLite 入库管线梳理

### 2.1 管线总流程（`materials import`）

```
resolveMaterials(按名+依赖闭包) → schema.TopoSort(依赖排序)
  → createMaterialTables(幂等建表+补列迁移)
  → resolveImportDeps(预解析康熙笔画, 注入而非回读库)
  └─ for each 物料:
        importOne:
          stat 源 → checksum.File
          if 指纹未变 && 主表非空 → 短路跳过(ADR-014)
          else → materialRegistry[def].Import:
                 读源 → 归一化(normalize.*) → 校验(validate.*)
                 → runImport(单事务 DELETE+INSERT 全量重建)
                 → registerMaterialState(登记指纹)
  → syncNameFreqTier(以 name_frequency 为唯一真源回填 hanzi_data.name_freq_tier)
```

关键护栏（均为 ADR 约定，已落地）：
- **单事务全量重建**：`DELETE FROM <表> + INSERT`，保证「同输入多次导入结果等价」(ADR-011)。
- **指纹短路**：`materialUnchanged()` 仅校验主表(表[0])非空+指纹一致，避免无谓重灌。
- **依赖注入替代回读**：康熙笔画由 `Import()` 预解析后注入 `importNamer`，消除「依赖已落库 + WAL 跨连接可见」两个脆弱前提(docs/34 A2)。
- **派生列单一真源**：`name_freq_tier` 由 `syncNameFreqTier` 在末尾统一归一化，不再由 `importNamer`/`importCharFreq` 两处维护(A3)。
- **AUTOINCREMENT 归零**：classics 三表的 `sqlite_sequence` 在导入后 DELETE，保证幂等。

### 2.2 物料注册表映射（JSON 源 → 物料 → 目标表）

| JSON 源文件 | 物料名 | 目标表 | 归一化/校验要点 |
|---|---|---|---|
| `raw/kangxi-strokecount.csv` | kangxi | `kangxi_strokes` | CSV→map，`normalize.Stroke` |
| `namer.json` | namer | `hanzi_data`,`char_groups` | `ResolveWuxing`(覆盖表>原值>部首兜底)；合并注入康熙笔画 |
| `name_frequency.json` | name_frequency | `name_frequency` | 仅 Tier≥2 回填字库档位 |
| `name_bigram_frequency.json` | name_bigram | `name_bigram` | key=char1+char2 约束 |
| `naming_quality.json` | naming_gate | `naming_gate` | 单字校验 |
| `forbidden_combos.json` | forbidden_combos | `forbidden_combos` | combo 校验 |
| `allowlist.json` | allowlist | `allowlist(entry,kind)` | char/combo/blessing → kind |
| `compliance_redline.json` | compliance_redline | `compliance_redline(entry,kind)` | state_org/place/person → kind |
| `yijing.json` | yijing | `yijing_hexagrams` | 卦校验、yao_ci 转 JSON |
| `zodiac.json` | zodiac | `zodiac` | 五行/兼容/冲突/幸运数转 JSON |
| `curated_names.json` | curated_names | `curated_names` | 去重；**仅删非用户行**，用户收藏(source=user_favorite)原样保留 |
| 20+ 经典 JSON（shijing/chuci/shici/...） | classics | `classics_books`/`sections`/`extracts`/`poem_entries` | `classics.LoadFromJSON` 物化；单文件解析失败跳过并可见 |

> 注册表 `schema.Definitions` 是「离线 JSON / 中间格式 / DB 表」三态的唯一规范来源；新增物料只在此登记一行即被导入器与校验器自动纳入。

## 3. 数据评估（实证）

**覆盖率（以 hanzi_data=8,105 为基准，根库实测）**
- 康熙笔画已填 **7,838 / 96.7%**，缺 267 字（多为生僻/异体）。
- 人名频率档 `name_freq_tier>0` 仅 **1,118 / 13.8%**；`name_frequency` 表本身仅覆盖 **2,237 / 27.6%** 字。
- 孤儿核查：`name_frequency` 中 0 条 char 不在字库；`name_bigram` 中 0 条 char1 不在字库（引用完整性良好）。
- `is_negative=1` 14 字、`is_rare=1` 99 字（用于候选池过滤）。

**门禁/合规分布**
- `naming_gate` 2,990、`forbidden_combos` 962、`compliance_redline` 98（person 24 / place 34 / state_org 40）。
- `allowlist` 当前 9 条**全部为 `blessing` 类**，无 char/combo 级白名单豁免条目（需确认是否符合预期）。

**双库分叉（风险点）**
- 物料层：根库 `materials_state` 无 `word` 记录、无 `words`/`data_meta`；backend 库反之。
- 运行期数据：根库 history=7、curated=52、gate_review=0；backend 库 history=3、curated=59、gate_review=7。
- 两者若被不同进程加载，会出现「门禁复审结论 / 用户策展名 / 历史记录」不一致。

## 4. 优化建议（按优先级）

### P0 · 一致性风险（必须处理）

**建议 1：确立单一权威库，消除双库分叉**
- 证据：两份 `namer.db` 行数/表集/运行期数据均已不同。
- 动作：确认运行时实际 cwd（建议锁定为 `backend/`，统一加载 `backend/namer.db`），**删除根目录游离 `namer.db`**；或在 `config`/部署中明确指定绝对路径，禁止依赖相对 cwd。
- 风险：删除前需先备份根库（其 history=7 多于 backend 的 3，可能含未被合并的历史）。

**建议 2：清理 backend 库孤儿表 `words`、`data_meta`**
- 证据：`words` 14,809 行（约 1.28 MB 文本，word 物料 2026-10-16.12 已退场）；`data_meta` 2 行（被 `materials_state` 取代）。两者均无运行期读取方。
- 动作：在 `backend/namer.db` 上 `DROP TABLE words; DROP TABLE data_meta;`（建议经迁移脚本，而非裸 DROP，保证可重放）。
- 风险：极低；删除后建议 `VACUUM` 回收空间。

### P1 · 数据质量（建议评估后处理）

**建议 3：补齐 `name_frequency` 覆盖缺口**
- 证据：仅 27.6% 字有频率数据、13.8% 命中 Tier≥2，余下 86% 字 `name_freq_tier=0`，频率维度评分退化。
- 动作：评估是否扩展 `name_frequency.json`（如纳入低频字 tier 分级、放宽 syncNameFreqTier 门槛），或在评分层对 tier=0 给出合理默认而非裸退化。

**建议 4：确认 `allowlist` 仅 blessing 是否符合预期**
- 证据：9 条全是 `blessing`，无 char/combo 级豁免。
- 动作：与门禁层设计（docs/33 M1）核对；若需字/组合级白名单豁免功能，应补充数据源与导入校验。

### P2 · 性能/体积（按需）

**建议 5：为 `name_bigram` 补 `(char1,char2)` 复合索引**
- 证据：仅主键索引，按首字检索会全表扫 12.5 万行。
- 动作：`CREATE INDEX IF NOT EXISTS idx_name_bigram_chars ON name_bigram(char1,char2);`

**建议 6：评估 `classics_poem_entries` 检索需求**
- 证据：仅主键索引，按 title/author/source/dynasty 或全文 LIKE 全表扫 1.2 万行。
- 动作：若前端需按作者/出处/朝代检索，补 `(source,author,dynasty)` 等索引；否则维持现状（规模可控）。

**建议 7：评估 `name_bigram` 长尾裁剪**
- 证据：12.5 万行是最大业务表之一，含大量极低 count 组合。
- 动作：若运行期只取 Top-N，可在导入期按 count 阈值过滤或保留 tier≥1，缩减约数万行。

## 7. 日志路径锚定与按天轮转（2026-10-21 附段）

用户明确指令两项需求：「日志目录固定：项目根/logs/」「统一文件名 namer-YYYYMMDD.log 按天轮转」。与本文 P0 项（DB 绝对路径）属同一治理范式：执行期产物路径一律锚定到模块根，杜绝随 cwd 漂移。

- **弃用 Lumberjack**：其语义是「单文件按大小滚动（+时间戳后缀）」，不满足「文件名本身即 namer-YYYYMMDD.log、按天一个文件」，改为在 `logger` 包内自实现 `dailySink`（跨天切换文件 + 保留 32 天过期清理）。
- **路径锚定（复用 `internal/paths` 范式）**：新增 `paths/module.go` 的 `FindModuleDir()`——从 logger 源文件位置向上探测 `go.mod`；`DefaultLogDir()` = 模块根/`logs/`（探测失败回落 `cwd/logs`，如 `go run` 单文件等非常规形态）。
- **`Config.OutputPath` 语义变更**：由「日志文件路径」改为「日志目录」；空值（默认）→ `DefaultLogDir()`，绝对路径原样，相对路径相对 cwd（显式传参场景保留）。`application.yml` 默认值与注释同步。
- **文件编码细节**：Init 改为 MultiWriteSyncer（dailySink + stdout），终端与文件共用 console 编码器，故 console 编码器关闭 ANSI 颜色（文件不能有色码）。
- **调用方收口**：`cmd/server/main.go` 的 `-log` flag 语义改为目录；`cmd/namer-cli/main.go` OutputPath 置空走锚定默认；`docker-compose.yml` 的 `NAME_LOG_OUTPUT_PATH` 由 `${LOG_DIR:-/app/logs}/namer.log` 改为 `${LOG_DIR:-/app/logs}`；docker 内锚点等价部署根（`/app/logs` 保持挂载卷语义）。
- **同行顺带修复**：预存断点 `internal/domain/fate/engine.go:705` 调用未定义的 `generateWithGeneration` 导致全仓无法编译——本批补齐该方法（字辈固定槽位 × 自由枚举，组合级过滤与评分口径复用 generateDoubleName 一致门禁），fate 包预存测试全绿。
- **验证**：`go build ./...` 全仓通过；`go test` 覆盖 paths / logger / config / server / handlers / fate 全部 ok；运行时冒烟实证 `backend/logs/namer-20261021.log` 生成且内容为中文日志、终端无色码。
