## 二、P1 发现（高危，均已人工复核）

### A1 · 自制 `syncOnce` 非线程安全，并发首调可致进程 fatal【已复核】

`internal/domain/fate/naming_chars.go:45-48, 317-327`

```go
type syncOnce struct{ done bool }
func (o *syncOnce) Do(f func()) {
    if !o.done { o.done = true; f() }   // 无任何同步原语
}
```

两个 goroutine 同时首次进入评分链路（`GetNamingCharInfo`/`IsNamingChar`）会双双执行 `initNamingIndex()`，并发写 `namingIdx` map → `concurrent map writes` **不可恢复 fatal，整个进程崩溃**。`AddNamingChar` 写 map 与读方亦无互斥。这是 `docs/28` W4（排除集竞态）修复后漏网的第三处同类问题。修法：直接用标准库 `sync.Once`（fate 包其他文件已 import sync，注释里「避免类型冲突」的理由不成立）。

### A2 · 非法日期吞错 → nil 解引用 panic，用户侧 500【已复核】

`internal/domain/bazi/lunar.go:42`（`GetLunarCalendar`）、`internal/domain/ziwei/ziwei.go:183`

```go
solarDay, _ := tyme.SolarDay{}.FromYmd(year, month, day)
lunarDay := solarDay.GetLunarDay()   // FromYmd 失败返回 (nil, err)，此处 panic
```

handler 对 `day` 只校验 `1..31`（`huangli_handler.go:52-54`），`2024-02-30`、`2023-04-31` 等合法格式但物理不存在的日期可穿透到领域层。`GetHuangli` 有局部 recover，但 **`GetLunarCalendar` handler 没有**；全局 `ZapRecovery`（`main.go:313`）兜底后表现为 **500 而非 400**。紫微排盘（`AnalyzeZiwei`，生产路径）同构吞错。修法：领域层处理 err 并返回 error；handler 用现有 validator 校验日期真实性。

### A3 · 大衍筮法实现错误：永远摇不出动爻【已复核】

`internal/domain/yijing/hexagram.go:368-396`（生产路径：`bazi/analyze.go:322` 每次八字分析都调用）

```go
result = sum % 4     // sum ∈ [3,12] → 结果 ∈ {1,2,3,8}
if result == 0 { result = 8 }
```

正确算法为三变归奇之和 `r1+r2+r3`，`（49 - 和）/ 4` 得 6/7/8/9（概率 1/16、3/16、5/16、7/16）。现实现值域 `{1,2,3,8}`，**6（老阴）与 9（老阳）永不可达** → `CastHexagramByDayan` 中 `num==9 || num==6` 恒假，**变爻恒为 0**，所有八字响应里的 `DayanHexagram/DayanInterpretation` 输出的是「无动爻的死卦」。附带：`randInt`（:398-401）每次调用 `rand.Seed(time.Now().UnixNano())`——已废弃 API，且并发同纳秒产生相同序列。

### A4 · 卦号映射错误：矩阵组合码当传统卦序号【已复核】

`internal/domain/yijing/hexagram.go:546`（`CastHexagramByDayan`，生产路径）

```go
hexagram := GetHexagramByNumber((upperTrigram-1)*8 + lowerTrigram)
```

`(upper-1)*8+lower` 是先天八卦矩阵索引，而 `GetHexagramByNumber` 匹配的是传统卦序（`HexagramList[i].Number`）。例：上兑下兑 → 组合码 10 → 查到第 10 卦「履」（上乾下兑），正确应为「兑」。同文件 `meihuaGuaNames`（:180）及其注释证明作者知晓两套编号的区别，但 `CastHexagramByDayan`、`CastHexagramByTime`（:476）、`GetHexagramByPlumBlossom`（plum_blossom.go:162-168）三处均未使用。**叠加 A3，八字响应中的大衍卦是「几乎随机的错卦」**。

### A5 · 紫微禄存表全错，擎羊陀罗随之全错【已复核】

`internal/domain/ziwei/ziwei.go:78`（生产路径：`adapters.go:81`）

### A7 · 收藏查询失败 → 前端无限重渲染白屏【已复核】

`frontend/src/app/result/page.tsx:51, 85-101`

```ts
const cachedFavorites = favoritesQuery.data?.success ? favoritesQuery.data.data ?? [] : [];
useEffect(() => { ...; setFavoriteStatus(status); }, [result, cachedFavorites, favoritesQuery.isPending]);
```

`/favorites` 请求**失败**（isError，data=undefined）且结果页有数据时：`cachedFavorites` 每次 render 都是新 `[]` → effect 重跑 → `setFavoriteStatus({})` 新对象必然触发重渲染 → 死循环 → "Maximum update depth exceeded" → ErrorBoundary **整页白屏**。成功路径因 React Query 缓存引用稳定而侥幸无事。修法：依赖改为 `favoritesQuery.data`/`isError`，或 `useMemo` 固定空数组引用。

### A8 · 前端 lint 质量门禁完全失效【已复核】

`frontend/eslint.config.js:1` + `package.json:10`

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@eslint/js'
```

`eslint.config.js` 引入 `@eslint/js`，但它不在 devDependencies、不在 pnpm-lock、不在 node_modules；且 `lint` 脚本的 `--ext` 参数自 ESLint 9（flat config）起已移除，本项目装的是 eslint 10.10.0。**`pnpm lint` 双重坏，一行业务检查都跑不了**——与 `docs/28` §1 描述的 e2e_check 失效是同一种「静默防线失效」。

### A9 · 「寓意关键词/偏旁选字」前后端全链路失效【已复核后端部分】

- **后端不消费**：全仓 grep 确认 `fate.GenerateOptions.MeaningKeywords`（`fate/types.go:54`）只有赋值链（`name_service.go:134→353`、`fate_name_service.go:140`、`name/generator.go:172` 声明），**engine/generator 无任何读取点**——字段被一路传递后丢弃。

用户输入关键词/选偏旁后，生成结果与不输入完全相同，而 UI 明确承诺「起名将优先从此来源选字」。属 A9 后端契约缺口 + 前端脆弱实现的双重问题。

### A10 · 伪造 X-Forwarded-For 可完全绕过 IP 限流【已复核】

`cmd/server/main.go:308-321` + `middleware/middleware.go:346` + `nginx/nginx.conf:200`

全仓 grep 无 `SetTrustedProxies/TrustedPlatform/RemoteIPHeaders`——gin v1.12.0 默认信任所有代理（`0.0.0.0/0`），从 XFF **最左侧**取 ClientIP；nginx `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` 是追加而非覆盖，客户端伪造值保留链首。攻击者每请求带随机 XFF 即可让每个请求落入新令牌桶，100 容量/10/s 限流形同虚设，同时污染访问日志。修法：`router.SetTrustedProxies(nil)` 并仅信任 nginx 覆写的 `X-Real-IP`。
