## 1. 管线现状概览（端到端调用链）

```
HTTP → NameHandler.Generate / GenerateWithAnalysis
  → FateNameService.GenerateWithAnalysis（fate_name_service.go:54）
      ├─ buildFilterOption()                        // 把请求转 Filter
      ├─ engine.NewSessionWithFilter()
      └─ session.Start() → goroutine run() → session.generate()
           1) BaziAnalyzer.Analyze()                // 八字 + 喜用神
           2) provider.GetSurnameStrokes()          // 康熙笔画
           3) provider.FindCharacters(query)        // 内存全表扫描 HanziData（约 8105 字）
           4) 合并 ExtraChars（诗词/经典外部注入）
           5) 字符级过滤：负面反馈快照 + 避讳长辈 + 大名需大命 + 硬禁用字 + 门禁字 + FilterOption
           6) 策展白名单收窄（PositiveScore>=85，extraChars 豁免）
           7) 喜用神五行收窄（降级保护 <80 不收窄）
           8) 预排序：charPotentialScore
           9) 双名笛卡尔积 N² / 单名 N 串行（按 CPU 分片并发）
              每个组合：组合级过滤 + 早停 + 7 维 RateName 评分 + ExcellentTable.TryPush
           10) ensureWuxingDiversity → 过滤 ForbiddenEntity → NameResult 列表
      → 输出映射 NameAnalysis
```

评分体系（rater.go:262 `DefaultRaters()`，权重之和 = 1.0）：

| 评分器 | 权重 | 说明 |
|------|------|------|
| WuxingRater | 0.24 | 五行八字匹配（命理层核心，不封顶） |
| WenHuaRater | 0.14 | 文化印象（策展字加分、诗词出处、共现加成） |
| YinYunRater | 0.14 | 音韵（声调、声母、韵母、谐音） |
| NoveltyRater | 0.14 | 新颖度（笔画搭配、语义差异化） |
| ShengXiaoRater | 0.11 | 生肖匹配 |
| BigramRater | 0.09 | 二字共现（诗词库） |
| SancaiRater | 0.08 | 三才（阴阳刚柔仁义） |
| FrequencyRater | 0.06 | 人名频率（语料统计） |

## 2. 关键 Bug 风险（按严重程度排序）

### 🔴 B1. 962 条清洗组合（荒谬双字）未被加载 — 治本缺失

**现象**：`backend/data/raw/清洗清单-门禁虚字.txt`（595 行）+ `清洗清单-荒谬组合.txt`（367 行）合计 **962 条双字组合**，与引擎注释（`engine.go:600-601`）"混入仲尼/若兮/七政/与砺 等 962 条垃圾"完全对应。但当前 `IsBadCombo` 只消费 `semantic_filter.go:86 forbiddenCombos` 硬编码表（28 条），**962 条清洗成果在仓库里沉睡**。

**根因**：`naming_quality.go` 只支持加载"单字门禁 JSON"，没有"双字组合 JSON"加载器；`semantic_filter.go` 的 `forbiddenCombos` 是代码内常量，没有加载函数。

**影响**：这些荒谬组合（如"仲尼/若兮/七政/与砺/与砺/以方/以时/以栋/以潜/以登/以言"等）会经过引擎全部评分链路，最终被 `WenHuaRater` 的共现加成（rater.go:388）拉高到 Top10（若共现库命中），或靠五行封顶豁免拉到 Top50。这正是 P0 推荐质量问题的最大根因。

### 🟠 B2. ExcellentTable 容量浪费（N×workers 倍内存）— P2 方案5 已修复

**位置**：`engine.go:540` + `table.go:81-89`

旧实现：每个 worker 创建一个容量 10000 的 ExcellentTable（localTable），合并阶段再创建一个容量 10000 的主表。8 核机器单次请求 = 9×10000 = 90K 容量堆（每个条目含评分/拼音/释义等~200 字节 → ~18 MB），而 topCount 通常仅 50~200。

**修正记录**：原报告曾担忧"worker 间对 (i, j) 对的枚举互相重叠"，经重读代码实际**没有重叠**——worker 按 i 分片、内层 j 全量，每个 (i, j) 对恰好被一个 worker 处理。真正的优化是减少 localTable 容量。已在 P2 方案5 修复：新增 `NewExcellentTableWithCap(capacity)`，worker 端容量取 `topCount*2`（最小 100），合并阶段仍用 `NewExcellentTable`（合并池大小与原逻辑一致）。

### 🟠 B3. 笔画口径混乱：姓用康熙、名用科学

**位置**：`engine.go:732-742`

```go
l1, l2, err := s.engine.provider.GetSurnameStrokes(input.Surname)  // 康熙笔画
...
totalStrokes += l1 + l2
...
totalStrokes += e.Stroke1 + e.Stroke2  // ← e.Stroke1/2 由 filter.GetCharacterStroke 决定，默认 ScienceStroke
```

**问题**：姓氏走康熙、名字走科学，**总笔画口径不统一**。AGENTS.md 规定河图数理与易经卦象解读用康熙笔画，目前连生成时回显的笔画数都口径混乱。

### 🟡 B4. `IsNonNamingChar` 双名循环已剔除（engine.go:602-604）、单名循环已剔除（engine.go:487-489）—— **OK**，记一笔无问题

### 🟡 B5. `ensureWuxingDiversity` 嵌套循环 O(N²) 去重

**位置**：`engine.go:1042-1053`

```go
for _, e := range entries {
    dup := false
    for _, r := range result {
        if r.Char1 == e.Char1 && r.Char2 == e.Char2 { dup = true; break }
    }
    ...
}
```

外层 N、内层 N → 实际是 O(N²)。建议用 `seenInResult map[string]bool`。

### 🟡 B6. `CheckBadHomophone` 不区分声调，误杀面较大

**位置**：`homophone.go:471-485`

```go
func CheckBadHomophone(pinyin string) (bool, string) {
    clean := stripTone(pinyin)
    for _, h := range BadHomophones {
        if clean == h.Pinyin { return true, ... }
    }
    return false, ""
}
```

例如拼音 `si` 既会命中"si=死"（不吉），又会被 **"思、丝、斯、四、寺"** 等常见好字的拼音命中——**逻辑错误**：谐音词不等于本字。`si` 拼音下的"思"作名字本字时不该扣"含不吉谐音:si=死"分。

### 🟡 B7. `BadPinyinCombos` 中性词误判

**位置**：`homophone.go:382-426`

`da dai`（打的，da=dai）、`huang se`（黄色，含"黄色"双重含义但日常是中性色彩）、`se qing`（色情）等组合过宽。`da dai` 在现代汉语中是中性动词词组，不应判为不良。

### 🟡 B8. 单 worker 持 ExcellentTable 容量 10000 浪费内存

**位置**：`engine.go:540`

`localTables := make([]*ExcellentTable, workers)` —— workers 个容量 10000 的堆 → 80K 内存/请求。建议容量自适应 topCount（一般 50~200），溢出即丢弃。

### 🟢 B9. 排除字段使用快照模式（engine.go:280-288）—— **OK**，注释明示

### 🟢 B10. Start 状态机校验（engine.go:98-117）—— **OK**

### 🟡 B11. `totalCount atomic.Int64` 与注释"总尝试组合数"不符

**位置**：`engine.go:464, 687`

注释（engine.go:711）说 "总尝试组合数"，实际 `continue` 早停前不计数，只统计实际 RateName 过的组合数 → 应改名为 `ratedCount` 或在 `continue` 前补 `Add(1)`。

### 🟡 B12. `homophone.go` 中 `Pinyin: "fu2"`（"妇"）带数字声调后缀，但 `stripTone` 只剥一个数字后缀，**其余同音拼音不带数字后缀**——这是历史数据 bug。

## 4. 推荐优化方案（按优先级排序）

### 🎯 方案1（P0 治本）：把 962 条清洗组合加载进 `IsBadCombo`

**收益**：极大。这是仓库里就有的现成资源（`data/raw/清洗清单-*.txt`），未被任何代码消费。

**步骤**：
1. 把两份 .txt 合并为 `data/forbidden_combos.json`（JSON 数组）
2. 在 `semantic_filter.go` 增加 `LoadForbiddenCombosFromJSON(dataDir)` 函数
3. `dataloader.go` 启动时装载
4. `IsBadCombo` 先查动态集合，未命中再查硬编码常量（保证向后兼容）

### 🎯 方案2（P0 治本）：修复 N² 笛卡尔积 worker 切分

最小改动：

```go
totalPairs := len(infos) * len(infos)
for w := 0; w < workers; w++ {
    startPair := w * (totalPairs + workers - 1) / workers
    endPair := (w + 1) * (totalPairs + workers - 1) / workers
    go func(startPair, endPair int) {
        for p := startPair; p < endPair; p++ {
            i := p / len(infos)
            j := p % len(infos)
            // 可选：i >= j 时利用对称性（拼音组合是顺序敏感的，需保留 i×j 和 j×i 两种）
            ...
        }
    }(startPair, endPair)
}
```

### 🎯 方案3（P1 治标）：统一笔画口径

`engine.go:732-742` 改成统一用康熙笔画（namer.json 当前没有 KangxiStroke 字段，需 namer_loader 增加读入）。短期内可保留 ScienceStroke 作为兜底，但目标全字段用 KangxiStroke。

### 🎯 方案4（P1 治标）：Homophone 本字豁免

`homophone.go:471-485` `CheckBadHomophone` 增加：本字 == BadHomophones.Word 本身时跳过扣分。

### 🎯 方案5（P2 性能）：ExcellentTable 容量自适应 + 去重改 map

```go
// engine.go:540
localTables := make([]*ExcellentTable, workers)
for i := range localTables {
    localTables[i] = NewExcellentTableWithCap(topCount * 2)

```

```go
// engine.go:1042-1053
```

`engine.go:475-708` 单名与双名逻辑在同一个 generate 函数里，但分支差异巨大。建议拆分。
