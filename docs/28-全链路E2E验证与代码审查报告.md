## 二、新发现的产品级风险：探索会话容量 32，FIFO 淘汰

E2E 首轮跑出「探索模式 400」时，手动调用却是 200。这个反差指向真实缺陷。

**根因**（实测确认）：`name_service.go:44` 的 `exploreStoreCapacity = 32`
是**进程级**容量，FIFO 淘汰最旧会话。复现：先生成一次拿到 `generation_id`，
再连续生成 35 次，回头用旧 ID 调 explore →

```
{"code":400,"message":"[Code: 400] 生成会话不存在或已过期，请重新生成"}
```

**影响**：单用户并发访问量下，用户在结果页停留期间只要发生 32 次其他生成
（其他用户、或多开标签页），点「换一批」必然 400。缓存无 TTL、无用户维度隔离，
容量对公共部署而言过小。E2E 自身就是受害者——全程生成约 48 个会话，基线
ID 早被挤掉，这也是工具要改成「就地重新生成再换一批」的原因。

**当前降级行为是得体的**（400 + 提示重新生成，不是 500 或空榜），E2E 已把
这个契约固化为检查项。但容量与隔离策略需要产品决策。

## 三、已实测确认的缺陷（Critical）

### F1 · 收藏功能几乎必然失败：前端传浮点，后端收整型

- 前端 `result/page.tsx:126`、`:153` 原样发送 `name.total_score`（如 `92.7`）
- 后端 `favorite_service.go:38` 为 `Score int \`json:"score"\``

Go 的 `encoding/json` 把小数反序列化进 `int` 会抛 `UnmarshalTypeError`，
直接 400。实测：

```
POST /api/v1/favorites  {"score":80.7,...}  → 400 请求参数格式错误
POST /api/v1/favorites  {"score":80, ...}   → 200
```

只有评分恰好整除时才能收藏成功。建议前端 `Math.round()`，或后端改 `float64`。

### F2 · 用户在首页填的「寓意关键词 / 偏旁选字」被全部丢弃

- `NameForm.tsx:43-47` 确实把 `{formData, keywords, selectedChars}` 传出去了

  `:150` 却 `onSubmit={handleSubmit}`
- 于是 `:103` 的 `keywords.split(...)` 用的是自己那个**从未被赋值**的 state，
  恒为空数组

后端 `meaning_keywords` 是真实存在且被消费的（`name_service.go:134` →
`fate/types.go:54` → `generator.go:172`），也就是说这是一条**接好了后端、
前端却没接上**的功能。TypeScript 不报错，因为「参数更少」是合法赋值。

### F3 · 结果页刷新后永久骨架屏，且无出口

`store.ts:86-89` 的 `partialize` 只持久化 `formData`，`generateResult` 不落盘；
`result/page.tsx:217-225` 在 `!result` 时只渲染骨架屏，**连导航栏都没有**。
刷新 = 死路，只能手动改地址栏。

### F4 · 数组下标当身份，筛选/换一批后崩溃

`result/page.tsx:202-210` 等处用 `topNames` 的下标存 `selectedName` /
`compareNames`。列表变短后 `topNames[i]` 为 `undefined`，`NameDetail` 里

### 8.1 W2 · viper 全局/局部实例断裂 —— 修复 + 连带发现第三处缺陷

**根因**：`Load()` 用 `viper.New()` 建**局部实例**并在其上 `SetDefault`/`ReadInConfig`，
但 5 个 getter（`GetString/GetInt/GetFloat64/GetBool/GetDuration`）读的是
`viper.GetViper()` —— 一个与之无关的**包级全局单例**。两者自始至终没有任何交集，
因此这 5 个 getter **恒定返回内置默认值**，配置文件里的值永远不会被读到。

**修法**：

1. 新增包级状态 `globalConfig` / `globalViper` 与 `sync.RWMutex`，
   `Load()` 成功后在写锁内同时存下配置对象与 viper 实例；
2. 新增 `getViper()`，5 个 getter 由 `viper.GetViper()` 改为 `getViper()`
   （未 Load 时 `getViper()` 返回 nil，各 getter 据此回落到 `defaultValue` 参数）；
3. `Get()` 由「每次调用都重新懒加载一份配置」改为「返回已加载的实例」。

**连带发现（第三处缺陷）**：写回归测试时 `TestGettersReadDefaultsWhenNoFile`
直接失败——

```
Load 失败: 加载配置文件失败: open ...\nope.yml: The system cannot find the file specified
```

调用方**显式传入**一个不存在的配置路径时，viper 返回的是 `*fs.PathError`
而不是 `viper.ConfigFileNotFoundError`，原代码只判后者，于是「找不到配置文件」
这个**完全正常**的场景被当成致命错误抛出，进程起不来。新增
`isConfigNotFound(err, configPath)` 同时识别两种形态（`SetConfigName`+`AddConfigPath`
模式返回 `ConfigFileNotFoundError`；`SetConfigFile` 模式返回 `*fs.PathError`），
统一回落默认值。

**实测证据**（`cmd/w2check` 一次性探针，配置文件写 `server.port: 8765`）：

| 读取方式 | 结果 |
|---|---|
| `config.GetInt("server.port", 0)`（修复后路径） | **8765**（文件值） |
| `viper.GetViper().GetInt("server.port", 0)`（旧路径） | **0** |

两行结果并列即证明旧代码读的是另一个对象。

### 8.2 W4 · 负面反馈排除集 —— 一处竞态 + 一处「功能完全失效」

原审查只记为「写加锁、读不加锁，是潜伏的 `concurrent map read and map write`」
（并注明"暂无调用点"）。实际动手修时发现**问题比记录的更严重**：

**缺陷 A（竞态，与记录一致）**：`isCharExcluded`/`isComboExcluded` 不加锁直接读 map，
其注释声称「并发安全由 s.mu 守护（generate 与 ExcludeChar 互斥）」——
该论断是**错的**：`generate()` 全程并不持有 `s.mu`（只在入口短暂持锁设置状态后即释放）。
因此「生成进行中调用 ExcludeChar」会与读形成 `concurrent map read and map write`，
这是 Go 运行时的**不可 recover fatal error**，会直接终止整个服务进程，不只是一个请求失败。

**缺陷 B（功能失效，本次新发现，危害高于 A）**：`Start()` 里无条件执行

```go
s.excludedChars  = make(map[string]bool)
s.excludedCombos = make(map[string]bool)
```

把调用方在 `Start()` **之前**设置的排除项**全部抹掉**。而 `Session` 接口契约
（`ExcludeChar` 注释）明确写着「后续重新生成时所有包含该字的候选将被过滤」，
即「先从界面排除 → 再重新生成」这一唯一合理用法。结果就是排除功能**从未生效过**。

实测（50 个结果）：

| 阶段 | `ExcludeChar("渝")` 后结果中含「渝」的数量 |
|---|---|
| 修复前 | **12** |
| 修复后 | **0** |

**修法（含读路径性能演进三阶段）**：

| 阶段 | 实现 | 结论 |
|---|---|---|
| ① 原始 | 读不加锁 | 有 bug（fatal error） |
| ② 首版修复 | 逐次 `s.mu.RLock()`，字段改 `sync.RWMutex` | 正确，但**热路径代价高** |
| ③ 当前实现 | `atomic.Pointer[exclusionSnapshot]` 不可变快照 + copy-on-write | 正确且**无锁** |

阶段②的代价是实测出来的：`isComboExcluded` 位于双名 N×N 笛卡尔积的**最内层循环**
（真实数据下每次生成调用千万次量级），即便 RWMutex 读锁只是原子计数，
累积起来仍让**串行吞吐下降约 20%**。

阶段③的做法：新增 `exclusionSnapshot{chars, combos}` 不可变结构体，
写方（`ExcludeChar`/`ExcludeCombo`/`ClearExclusions`）在写锁内**复制后原子发布**
新快照；读方仅一次原子指针加载 + 一次 map 查找。
关键约束是**先复制、后发布**——若直接把可写 map 放进快照，写方后续写入就会命中
读方正在遍历的同一份 map，等同复现缺陷 A。排除集通常只有几个元素，重建成本可忽略。
`nil` 快照等价于「空排除集」，因此普通请求（无任何排除）零额外开销。

微观基准（`engine_exclusion_race_test.go`，`-benchtime=3000000x`）：

| 场景 | ns/op | 说明 |
|---|---|---|
| `Empty`（无排除项） | **1.1** | 线上绝大多数请求的真实形态，近乎零成本 |
| `Populated`（8 项排除） | ~58（单核）/ ~69（默认多核） | |
| `Hit`（乱序传入已排除组合） | ~66 | 验证排序归一化仍生效 |

> 注：多核下略高源于机器核间缓存同步，与本机 i7-4710MQ 的老旧架构有关，
> 非实现问题（单核 58ns 为真实指令成本）。

**同时修正的时序语义**：②阶段注释写的是「排除集在 `generate()` 入口被一次性快照消费，
故 `ExcludeChar` 必须在 `Start` 之前调用」。改为 `atomic.Pointer` 后，
快照指针是**每次调用时**加载，因此生成进行中新增的排除项会**立即**对尚未评估的组合生效——
比②阶段更及时。`Start()` 中不再需要为「无排除项」预建空 map。

**连带修正的误导性注释**：`engine.go` 中三处描述读路径加锁方式与「一次性消费」
语义的注释已同步更新，避免下一个人被旧注释误导。

**回归测试**（`internal/domain/fate/engine_exclusion_race_test.go`，3 条 + 3 个基准）：

#### 8.5.1 进一步定性：该判据在当前设计下无法大于约 1.4×

追查判据的数学模型后发现，**加速比存在一个由设计决定的上限，与实现无关**：

1. `generateDoubleName` 中双重枚举的 worker **总量被进程级信号量
   `candidateWorkerLimit` 钳制在 `runtime.NumCPU()`**（本机 8），
   即无论多少并发请求在飞，同时执行枚举的 worker 合计不超过 8，后来者排队。
   这一设计正是 P2-7 有意为之（杜绝「并发请求数 × NumCPU」超订）。
2. 由 Little 定律，若 16 并发请求的墙钟 `totalWall` 内处理的请求量为
   `allTotal`，则**平均在飞请求数** = `allTotal / totalWall × Tₙ`
   （`Tₙ` 为单请求平均服务时长）。设 8 个 worker 被占满（枚举段占总时长的 f），
   则 `allTotal / totalWall × Tₙ ≈ 8 / f`。
3. 而加速比 = `allTotal / totalWall × T₁`。当并行度尚未饱和时 `T₁ ≈ Tₙ`，
   代入得 **加速比 ≈ 8 / f**。该比值只取决于「枚举段占总服务时长的比例」，
   与串行基线快慢**无关**。

实测 1.33× 反推 `f ≈ 6`（>1），说明**并行度尚未饱和**——系统中存在**串行段**
（`analyzer.Analyze` 八字排盘、`FindCharacters` 加载字库、写库与响应编码等）
根本不吃 8 个 worker，因此 16 并发的墙钟被串行段主导。

**结论**：只要 worker 总量继续钳在 NumCPU，而单请求服务时长里存在约 1/8 的
纯串行段，该比值就**永远不会超过约 8×f 倒数之外的值**；且串行段越快，
比值反而越高（因为比值 ≈ 8/f，串行段变快 → f 变小 → 比值变大）。
换句话说：**把串行路径优化得越好，这个判据越好过；而当前它难过，
恰恰因为串行段太慢**——判据方向与直觉相反。

**建议改法（待决策，本轮未实施）**：把「吞吐加速比 vs 固定阈值」替换为
更能反映超订防护的两条判据：

1. **单请求 p95 不随并发恶化**：16 并发下的 p95 不得比串行 p95 高出
   一个可接受倍数（真正要防的是超订导致的排队延迟爆炸）；
2. **并发吞吐不低于串行吞吐**：即 `allTotal / totalWall ≥ 1 / serial`，
   断言「多请求并行至少不比串行慢」，不设倍数门槛。

这样既守住 P2-7 的初衷（不超订），又不会因串行路径变快而误判失败。

### 9.1 W3 · 取消/超时被伪装成成功

**原记录**：「ctx 取消时提前 `return` 跳过 `wg.Wait()`」。

**实测修正**：先核对了一遍——两个 `cancelled(ctx)` 处的 `return` 都是**从 goroutine
内部返回**，而 `defer wg.Done()` 由 defer 保证执行，因此 `wg.Wait()` **并不会被跳过**。
原记录的因果链是错的，但**后果描述是对的**：会话确实会「被取消却报告成功、榜单为空」。

**真实根因**：真正的洞在另一处——取消这件事在**领域层完全不可见**。
各枚举循环在 `cancelled(ctx)` 为真时只是静默 `return`（退出该 worker），
主流程照常往下走、照常组装 TopNames、照常 `return nil`。于是：

| 观测点 | 修复前（ctx 已取消） |
|---|---|
| `Wait()` | **返回 `nil`**（上层看不出被取消） |
| `State()` | `SessionStateFinish` |
| `Result()` | 一份**被截断的**榜单 |

**实测证据**（`TestSessionCanceledContextReportsError` 跑在修复前的代码上）：

```
engine_cancel_test.go:49: ctx 已取消却 Wait() 返回 nil —— 上层会拿到被截断的榜单当成成功
--- FAIL: TestSessionCanceledContextReportsError (0.21s)
```

原设计把兜底责任推给了调用方（`fate_name_service.go:156` 确实补了 `ctx.Err()` 检查，
并有 `fate_name_service_e2e_test.go` 覆盖）。但这属于**每个调用方都必须记得做对**的事，
漏一个就静默返回垃圾数据。

**修法**：在 `generate()` 返回前统一判定 `ctx.Err()`，
非 nil 时以 `fmt.Errorf("名字生成被中止: %w", err)` 上抛；同时 `run()` 中据此把
会话状态标为 `SessionStateCanceled` 而非 `Failed`（前者是调用方主动中止/超时，
后者是生成故障；上层可据此决定「重试」还是「改参数」）。

**回归测试**（`internal/domain/fate/engine_cancel_test.go`，4 条）：
取消路径 `Wait()` 必须返错且可 `errors.Is(err, context.Canceled)` 判定、
`State()` 必须为 `Canceled`、`Result()` 必须为 nil；
超时路径同理但判定 `DeadlineExceeded`（handler 据此返回 503 而非 500）；
正常路径不受影响（仍 `nil` + `Finish` + 有名字）；
`Stop()` 主动中止也必须可感知。

### 9.2 W5 · 未列举错误码降级为 200

**实测**（修复前的 `getHTTPStatus`）：

| 传入 code | 映射出的 HTTP | 判定 |
|---|---|---|
| 400 / 401 / 403 / 404 / 422 / 500 / 503 | 同值 | ✅ |
| **409**（冲突） | **200** | ★ 被当成成功 |
| **429**（限流） | **200** | ★ 被当成成功 |
| **999** | **200** | ★ 被当成成功 |
| **0** | **200** | ★ 被当成成功 |

客户端普遍以 `res.ok`（等价 `status < 400`）判成败，因此这些错误**会被静默吞掉**：
用户看到「没报错但也没数据」的页面，前端不会重试，监控也收不到信号。

**影响面核实**（这一点很重要，决定了修复的紧迫性）：全仓 grep 发现

- 现有 **53 处** `response.SuccessJSON/ErrorJSON` 调用实际只传 `400/404/500/503`，
  全部在名单内 → **当前无活跃故障**；
- 而 `response` 包里导出的 8 个错误常量（`BadRequest`/`NotFound`/…）**零引用**，
  已在 §4 死代码清单中；
- 因此 W5 是**潜伏陷阱**：任何新增一个非常见错误码（409/429/451…）的调用点，
  或任何试图改用那些导出常量的写法，都会立刻踩中。

**修法**：把白名单改为**按区间兜底**——合法的 `400-599` 直接透传（涵盖 409/429/451 等
全部客户端/服务端错误语义），其余任何值（0、负数、1xx/2xx/3xx、>599）一律归为
**HTTP 500**。兜底到 500 而非 400 的理由：写错状态码是**服务端缺陷**，
归 5xx 才能被监控告警捕获；归 4xx 会被当作客户端问题而长期潜伏。

**顺带清理**：删除那 8 个零引用的导出错误常量（属 §4 死代码清单内），
避免它们成为「看起来能用、实则一用就把错误降级成 200」的诱饵。

**回归测试**（`internal/application/response/response_test.go`，3 条）：
`getHTTPStatus` 表驱动覆盖原白名单 + 未列举合法码（409/429/451/599）+ 越界值
（0/-1/201/301/999/399/600）；`ErrorJSON` 端到端断言非法码不落入成功区间
**且响应体仍保留原始业务码**（便于排障时区分「写错码」与「真 500」）；
`SuccessJSON` 未受波及。

### 9.3 W6 · 每请求重复预分配 cap=10000 的表

**根因确认**：`generate()` 先 `NewExcellentTable()`（容量恒 10000），
紧接着 `generateDoubleName()` 末尾又 `*table = NewExcellentTable()` 重造一份。
第一份**从未写入任何条目**就成了垃圾。

2 个 int 等）重新估算约 200 字节/条目，即 **10000 × 200B ≈ 2MB/请求**
（堆切片 + 两个初始 map 桶），原估计偏大一倍，量级结论不变。

**修法**：
1. 建表容量改为 `topCount * 10`（即下游 `poolSize`/Top10N 的真实规模），
   带 `minExcellentTablePoolSize = 1000` 下限防小 `topCount` 时堆频繁替换；
2. `generateDoubleName` 的 `table` 参数由 `**ExcellentTable` 改为 `*ExcellentTable`，
   合并分片时就地 `TryPush` 到调用方传入的表，**不再重造**。

必须用 `NewExcellentTableWithCap`（保留去重）而非 `NewExcellentTableUnique`——
跨分片合并时 `Char1+Char2` 可能重复，去重能力是必需的。

**实测证据（等价性）**：改造前后对同一组入参取榜单指纹，**逐字节一致**：

| 入参 | 修复前容量 | 修复后容量 | TopNames |
|---|---|---|---|
| 王/male/双名/Count=50 | 10000 | 1000 | **50 个名字、顺序、分数完全相同** |
| 李/female/双名/Count=50 | 10000 | 1000 | **完全相同** |
| 张/male/单名/Count=20 | 10000 | 1000 | **完全相同** |

即：纯粹的内存优化，**零行为变更**（每次请求少分配约 2MB 垃圾）。

单名路径容量同样自适应。

| 探针 | 结果 |
|---|---|
| `mode=ro` 上 `Exec("PRAGMA journal_mode=WAL")` | **返回 `nil`，不报错** |
| 是否有 Warn 输出 | **没有**（既然不报错，Warn 分支根本不进） |
| 库原处 delete 模式时执行该语句 | 文件头偏移 18/19 字节 `(1,1)` → **`(2,2)`** |
| 新开的只读连接读到什么 | `journal_mode = "wal"` |

即 `1=legacy`、`2=WAL`，文件**被真的改写了**。所以这条语句不是「无效噪音」，
而是「**一个显式声明只读的连接在悄悄写盘**」。

在 `NewStore` 的当前调用顺序下它恰好无害（上面的写连接已把库设为 WAL，
此处退化为 no-op、不产生写入），但它是一个**依赖调用顺序才安全的陷阱**：

- 任何「先建只读连接、后建写连接」的重构 → 变成真实写入；
- 对外部只读副本（非 WAL 库）误用 → 修改了不该修改的文件。

**修法**：删掉该语句，改为**只读校验**——读回 `journal_mode` 并与预期比对，
不一致才告警（这反而会捕捉到「读写连接指向了不同文件」这个真正值得报警的情况）。

**回归测试**（`internal/infrastructure/database/sqlite/store_journal_mode_test.go`，2 条）：

- `TestReadOnlyConnectionMustNotWriteFile`：把上述反直觉行为**固定下来**。
  用「直接读文件偏移 18/19 字节」这一**文件级**依据（不依赖任何连接，
  因此既能识破「连接自称 WAL 但文件没变」的假象，也能识破「只读连接真改了文件」）。
  若将来驱动收紧行为改为报错，用例会走另一分支并提示重新评估——不会假绿。
- `TestNewStoreDoesNotAlterExistingJournalMode`：打开已 WAL 的库后模式仍为 WAL，
  且只读连接能正常查询（证明删掉 PRAGMA 没有破坏读路径）。
