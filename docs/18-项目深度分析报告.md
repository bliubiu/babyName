### 2.2 正向评价

- **DDD 4 层结构基本遵守**：domain 不依赖 infrastructure，依赖方向正确。
- **适配器模式正确**：`HanziDataProvider` 实现 `fate.CharacterProvider`，`BaziAnalyzerAdapter` 实现 `fate.BaziAnalyzer`。
- **EngineFactory 模式**：支持测试注入和 raters 自定义。
- **fate engine Session 设计**：异步生成 + 生命周期管理（Pending→Generating→Finish/Failed/Canceled），接口抽象合理。
- **Rater 链**：可组合、可扩展的评分器设计，权重可配置。

### 2.3 架构问题

#### 🔴 P1 — `services.go` 1,145 行 God Object

`NameService` 承担了 15 个 method，职责包括：

| Method | 行数 | 职责 |
|--------|------|------|
| `Generate()` | 30 | 名字生成主入口 |
| `GenerateWithAnalysis()` | 73 | 带分析的名字生成 |
| `performBaziAnalysis()` | 22 | 八字分析 |
| `generateNames()` | 91 | 名字生成（路由到 fate/旧引擎） |
| `generateNamesViaFate()` | 45 | fate 引擎调用 |
| `calculateHexagramAndZiweiParallel()` | 62 | 卦象+紫微斗数并行计算 |
| `buildResponse()` | 22 | 响应构建 |
| `logGeneration()` | 42 | 日志记录 |
| `GetByID()` | 60 | ID 查询 |
| `GetNameDB()` | 6 | 取数据库引用 |

> **问题**：一个 Service 同时处理生成、分析、卦象、日志、查询，违反了单一职责原则。建议拆分为 `NameGenerationService`, `BaziService`, `ReportService`。

#### 🟡 P2 — 接口定义位置不当

`interfaces.go` 中定义了：
- `BaziAnalyzer`（应由 `domain/bazi/` 定义）
- `NameGenerator`（应由 `domain/name/` 定义）
- `EnhancedNameAnalyzer`（应由 `domain/name/` 定义）
- `ZodiacFinder`（应由 `domain/zodiac/` 定义）

> DDD 规范：接口应在 domain 层定义，infrastructure 层实现。当前定义在 application/services 层。

#### 🟡 P2 — 手工 DI 无工具链

所有依赖注入在 `main.go` 中手工组装（约 80 行）。每次新增服务类型都需要：
1. 新增接口定义
2. 新增 `WithXxx()` Option 方法
3. 在 `main.go` 中组装

> 建议引入 `wire` 或 `dig` 工具链管理依赖。

#### 🔴 P1 — `domain/name/` vs `domain/fate/` 职责重叠

**现状**：两个引擎共存，但 `domain/name/`（4,563 行，5 文件）仅在 `fateService == nil` 时执行。

| 文件 | 行数 | 状态 |

| `generator.go` | 1,295 | 🔴 基本休眠 |
| `enhanced_generator.go` | 1,807 | 🔴 基本休眠 |
| `name_filter.go` | 687 | 🟡 可用 |

## 三、性能分析

### 3.1 热点路径

#### 🔴 P0 — fate 引擎 O(n²) 全排列

```
generate() 核心循环：
  validChars := FindCharacters(query)   // ~3,500 字
  for _, c1 := range validChars {       // 3,500
      for _, c2 := range validChars {   // 3,500
          // 评分 + TryPush
      }
  }
```

- **时间复杂度**：O(n²) = ~1,225 万次迭代（双名）
- **ExcellentTable**：最小堆实现，`TryPush` 为 O(log 100) ≈ O(1)
- **估算耗时**：500ms — 2s 每次生成请求
- **优化方向**：笔画过滤/部首过滤前置，减少迭代基数

#### 🟡 P1 — 每次生成都查库

`FindCharacters(query)` 每次 session 都从 SQLite 加载全量字库（~3,500 行）。字库数据很少变化，适合一级 LRU 缓存或 `sync.Map` 内存持有。

#### 🟡 P1 — 热路径内存分配

每次循环创建 `NameCandidate{...}` 结构体，双名场景 ~1,225 万次分配。可通过 `sync.Pool` 复用。

#### 🟡 P2 — Rater 中 `fmt.Sprintf` 频繁调用

每个 Rater 的 `Rate()` 使用 `fmt.Sprintf` 构建 `details` 切片，每次候选都执行。字符串拼接在 O(n²) 循环中放大。

### 3.2 SQLite 配置

| 参数 | 当前值 | 状态 |
|------|--------|------|
| MaxOpenConns | 16 | ✅ 已优化 |
| MaxIdleConns | 8 | ✅ 已优化 |
| WAL 模式 | 启用 | ✅ |
| 读写分离 | 否 | 🟡 可优化 |

### 3.3 并发模型

- **fate session**：在独立 goroutine 中异步运行，`context.WithCancel` 支持取消 ✅
- **互斥锁策略**：generate() 运行时在锁外复制快照，避免长时间持锁 ✅
- **旧引擎 vs 新引擎**：旧引擎 4 worker batch，新引擎同步迭代。新引擎评分更细但速度可能更慢。

### 4.3 缺失的功能

#### ❌ P2 — 三才评分 Rater 未实现

Rater 链中仅有 4 个 Rater（Wuxing 35% / WenHua 25% / YinYun 25% / ShengXiao 15%）。`name.Name` 有 `SancaiScore` 和 `SancaiAnalysis` 字段，但 fate 引擎中没有对应的 `SancaiRater`。

AGENTS.md 三层体系明确要求：

```
┌─────────────────────────┐
│  字象（血肉）            │ ← WenHuaRater / YinYunRater
├─────────────────────────┤
│  数理（骨架）            │ ← SancaiRater（缺失）
├─────────────────────────┤
│  命理（根基）            │ ← WuxingRater / ShengXiaoRater
└─────────────────────────┘
```

数理层（河图数理、姓名卦象、阴阳消长）目前只在 API 响应中有 `hexagram` 字段，在评分中未体现。

#### 🟢 P3 — 诗句语义匹配可增强

`WenHuaRater` 中诗词出处加 8 分，共现加分 `GetBigramScore` 返回个位数加分。匹配仅基于两字是否在同一句中出现，未做更细粒度的语义亲和度分析。
